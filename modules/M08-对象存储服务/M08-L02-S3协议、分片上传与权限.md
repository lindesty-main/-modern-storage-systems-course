## 1. “兼容 S3”不是一个布尔值

“S3”常被用来指 Amazon S3 产品、S3 REST API 家族、AWS SDK/CLI 的签名行为，或第三方产品对部分 API 的兼容声明。这些对象不是同义词：

- **Amazon S3** 是 AWS 托管产品，其服务文档描述 AWS 对具体区域/功能的产品行为和承诺；服务端会持续更新，课程不能固定 AWS 端软件构建。
- **S3 API** 是通过 HTTP 请求表达 bucket/object 操作的一套接口约定，并非每个实现都支持所有 API、条件头、错误码或可选功能。
- **Ceph RGW** 在具体 Ceph release 中实现一组 S3 风格操作。应按该版本的支持矩阵和配置验证，不能由“支持 S3 API”推出与 AWS 全面行为等同。
- **MiniStore M08** 是本地 C++ CLI 子集。它没有 HTTP endpoint、REST 路由、AWS SDK binding、认证或 SigV4；AWS CLI 指向它不会工作。

API 兼容性应写成矩阵：版本/配置 × 请求方法和 operation × 必需/可选 headers × payload/签名 × 返回状态/错误 × 一致性/并发 × 权限策略。最小测试集也不等于通用认证证书。

| 能力 | MiniStore M08 | AWS S3 产品 | 本课程 Ceph RGW 选修目标 |
|---|---|---|---|
| 接入方式 | 本地 argv + stdin/stdout | AWS HTTPS endpoint、S3 API | 本地 RGW endpoint、版本化 S3 API 子集 |
| 认证/授权 | 无用户身份；依赖本机 OS 账户/目录权限 | AWS 身份与策略体系、签名请求 | RGW 用户/密钥和目标 release 的策略/功能 |
| PUT/GET/DELETE | 一个 CLI 操作；单对象 ≤1 MiB | HTTP API；支持能力按 AWS 文档 | 仅对课程操作清单逐项验证 |
| LIST | 本地全量扫描、可选简单前缀、无分页 | ListObjectsV2 等服务接口，分页 token | 对已测操作/分页规则记录结果 |
| Multipart | 不支持 | Initiate/UploadPart/Complete/Abort 等流程 | 支持项和差异以 Ceph release 文档/试验为准 |
| 产品承诺 | 不声明分布式/服务级承诺 | AWS 产品文档与合同/服务配置 | 不继承 AWS 服务承诺；看 Ceph 实现/部署 |

表中的 AWS/RGW 是概念边界，不是课程已经在对应环境完成所有接口测试的声明。MiniStore 必做验收只使用自己的测试客户端。

## 2. HTTP API 与 SigV4 的作用边界

典型 S3 风格请求通过 HTTP method、bucket/object path 或 host、query parameters、headers 和 body 表示操作。成功响应/错误响应会包含状态码、header/body；list 常分页并返回 token。真实客户端还要处理 TLS、DNS、连接复用、chunked/流式 payload、重试策略、时钟和区域配置。

**AWS Signature Version 4 (SigV4)** 是请求认证签名机制的一部分。概念上客户端规范化 method、URI、query、指定 headers 和 payload hash，派生 credential scope/key，再计算签名；服务端用同一规则校验凭据、请求完整性和时间/范围。规范化差异会导致签名错误，即使底层对象 API 请求本身正确。SigV4 不是授权策略：认证成功只说明请求由可验证凭据签出，服务仍需判断这个 principal 是否允许对指定资源执行指定 action。

多种常见差异源：

- path-style 与 virtual-host-style 地址、bucket 位于 Host 还是路径中的处理；代理重写 URL 会影响 canonical request。
- 签名包含的 header、payload hashing、临时 session token、region/service scope、时钟偏差和 URL 编码。
- 各实现对 ACL、桶策略、对象锁、版本化、标签、生命周期、加密、校验算法、事件通知、错误 XML 和分页 token 的支持程度不同。
- `ETag` 不保证总是内容 MD5；服务器端加密或 multipart 会造成不同定义。
- SDK/CLI 可能默认重试某类错误。若响应丢失，重复操作在某些场景安全、某些场景会增加版本或留下额外资源；不能只凭“PUT 幂等”假设所有副作用完全相同。

所以做互操作时先固定一个小的 API 操作清单与版本，再逐项记录状态码、header、返回字段、读取结果、权限结果和失败清理；不使用“客户端命令退出 0”代替一致性/耐久性证明。

## 3. S3 Multipart Upload：对象级会话状态机

浏览器 `multipart/form-data` 是 HTTP 表单 body 中多个字段/文件段的编码，不自动代表对象服务把内容切成多个独立上传 part。S3 Multipart Upload 是由服务端维护的**有状态上传会话**：

```text
CreateMultipartUpload
        │ 返回 UploadId（绑定 bucket + key）
        ▼
UploadPart(partNumber, UploadId, bytes) ──可并行/重传──┐
        │ 每个成功 part 返回 ETag/校验信息             │
        ├── ListParts / 查询上传状态 ──────────────────┤
        │                                              ▼
        ├── AbortMultipartUpload                 CompleteMultipartUpload
        │                                              │ 按 part number + ETag 提交
        ▼                                              ▼
   清理未完成内容                              完成一个可见的对象版本
```

精确的 part 数量、编号范围、最小 part 大小（最后一片的例外）、总对象大小、校验算法、并发限制和成本，必须读取目标产品版本的限制文档，不能复制一篇旧博客的数字当作所有兼容实现的统一值。

### 客户端/服务端分别做什么

1. **Initiate：**客户端请求创建会话，保存 upload ID；服务端可能记录元数据、用户权限及初始化选项。这个 ID 不是长期对象 key，也不是可公开分享的 bearer token。
2. **UploadPart：**客户端按 part number 发送字节。网络中断后可对某片重试/覆盖（以产品语义为准）；客户端需安全保存 part 状态/ETag，服务端保留已收片段。
3. **断点续传：**通过 ListParts 或应用自己持久化的 manifest 对照已经完成的片，校验 upload ID / part number / ETag，再补发缺失片。客户端进程的“文件偏移”不能单独证明服务端已接受该片。
4. **Complete：**客户端按排序后的 part number 和服务端返回的 ETag/校验数据提交完成请求。服务端检查 parts 后组装/逻辑发布对象；成功响应丢失时，调用者不知道提交是否完成，需要检查目标对象及 multipart 会话状态。
5. **Abort：**失败或用户取消后显式中止，释放未完成部分。Abort/并发上传之间的具体时序需要按产品文档处理；已在飞的上传可能造成中止后仍需再次检查/清理的情况。

### 失败窗口与清理清单

| 故障窗口 | 可能状态 | 恢复/清理思路 |
|---|---|---|
| 客户端在 Initiate 后崩溃 | 有 upload ID、无 part 或只上传部分 part | 保存 session 清单；按 bucket/key/upload ID 查询并 abort |
| 某个 UploadPart 超时 | 客户端未必知道服务端收完没有 | 查询服务端 parts/校验；按接口语义重试，不仅依赖本地传输进度 |
| Complete 请求超时 | 服务端可能已完成，也可能未完成 | 先 HEAD/GET 目标对象并检查上传会话，再决定重试/清理；避免误删已提交数据 |
| 客户端无法回收 upload ID | 未完成片段长期占用容量/费用 | 任务队列定期列举、告警和 abort；配置生命周期规则作为兜底并验证目标服务支持 |
| Abort 与仍在发送的 part 竞争 | abort 返回后仍可能有请求在途或状态传播 | 按产品文档查询/重试 abort，再检查未完成会话；不要只看一次本地成功日志 |
| metadata DB 更新成功而对象完成失败（应用编排） | 业务关系指向缺失对象 | 应用 reconciliation、幂等状态机和孤儿记录/对象清理，不假定多服务事务 |

AWS 的 multipart API 文档描述了 UploadId、part、Complete/Abort、ListParts/ListMultipartUploads 和不完整上传清理；AWS 也提供生命周期自动 abort 规则。生命周期清理有延迟且只按对应配置执行，不替代请求失败后的业务恢复/监控。RGW 等实现的具体支持和边界应对当前版本做验证。对象 ETag 在 multipart 场景不可普遍当成整文件 MD5。

MiniStore 没有 upload ID、part 暂存、分片状态、Complete/Abort 或生命周期清理。超出 1 MiB 会在写入前作为输入错误拒绝，不会生成临时 multipart 会话。不要用多个 `object-put` 片段拼接来冒充 multipart：MiniStore 的 put 是完整覆盖，不是 append/compose。

## 4. 权限：认证、授权、对象名和网络入口

安全模型至少分成四层：

1. **传输保护：**TLS 保护凭据和 payload 在网络中的传输；非 TLS 明文签名请求也可能泄露数据/元数据或被重放攻击。是否强制 TLS 由服务/代理配置决定。
2. **身份认证：**SigV4/API key/临时身份回答“请求者是谁”。访问密钥应可轮换、限制生命周期，并避免硬编码进仓库、Docker image、shell history 或公开日志。
3. **授权：**IAM/桶策略/访问点/角色等决定 principal 可对哪个 bucket/key 执行哪些 action，以及是否满足来源、网络或标签条件。按最小权限分配读、写、列举和删除，不给客户端不需要的 `ListAllMyBuckets` 或管理权限。
4. **公开访问与分享：**默认私有；公开读必须经过显式威胁评估。短期预签名 URL 是 bearer capability，谁拿到都可在有效期内使用，应缩短过期时间、限制对象/方法、避免日志泄漏。AWS 的 bucket-owner-enforced 等默认建议是 AWS 产品实践，RGW/其他实现的 ACL 语义需单独确认。

额外注意：

- Bucket policy、ACL、Unix mode 与 MiniStore 的 `0700` 目录不是同一授权系统。MiniStore 当前没有用户/租户字段、身份认证、对象级访问控制或 per-bucket policy；只能依赖运行进程的本地 OS 身份和专用私有目录。
- 避免把用户提供的 object key 直接拼成文件路径。MiniStore 把合法 key 编码进内部 KV 名称而非文件名；实际服务必须做长度、编码、规范化、代理路由和跨租户隔离检查。
- 别因 URL 难猜就当它是权限控制；随机 file ID/URL 可能被日志、浏览器 referrer、代理和统计系统传播。
- 云资源、bucket policy、public access block 和服务端加密默认值均属于具体 provider/账号配置；本地兼容实现不能替代核对。
- 上传、删除和覆盖应有审计与告警；只对可信管理员提供 lifecycle、policy、access key 等控制面权限。

## 5. MiniStore 的错误与并发范围

本地对象 CLI：

```sh
ministore object-put    --dir DB BUCKET KEY < FILE
ministore object-get    --dir DB BUCKET KEY > FILE
ministore object-delete --dir DB BUCKET KEY
ministore object-list   --dir DB BUCKET [PREFIX]
```

`object-put` 每次从 stdin 收集最多 1 MiB bytes，检查超限后不追加 WAL；成功记录先写完整 WAL record、`fdatasync`，再发布内存 map，返回 sequence/size。覆盖是完整 payload 替换。`object-get` 将 bytes（包含 NUL）写到 stdout；`object-delete` 只删除存在对象；缺失 get/delete 返回码 3。非法 bucket/key/过大 payload 返回码 2。数据库锁/格式/IO 错误返回码 1；第二个同时打开者因 `LOCK_EX|LOCK_NB` 立即报错而不是等待。

同步成功后的调用响应可能在网络/终端/管道丢失；当前 MiniStore 是一个本地进程命令，但同样存在“日志已同步，响应未到调用者”的窗口。同步错误可能发生在部分/全部数据已进入当前内核路径之后。两种情况都不应把失败响应解释为“确定没有写入”，应通过新命令查询对象，再依据业务幂等性决定动作。

这些行为不构成服务端 S3 语义：MiniStore 没有客户端请求 ID、条件写、版本 ID、请求重试协议、并发读写或权限策略。一次成功 object-put 后的一次新进程 get 证明本次测试环境中可重新打开读取；不证明真实断电、远端副本或多租户正确性。

使用专用测试 bucket、少量合成文件，只运行课文或 Lab 明列且 RGW 文档确认支持的操作。不要复用 `~/.aws` 中的云凭据；在自己创建的临时目录中保存本机 RGW 专用 profile，权限设为 `0600`，运行结束后由临时目录清理。下面是 Bash 形状示意，endpoint/已有 bucket 需按本机环境替换；`read -s` 隐藏输入，不要把实际密钥写到命令行或仓库：

```sh

export AWS_SHARED_CREDENTIALS_FILE="$RGW_TMP/credentials"
export AWS_CONFIG_FILE="$RGW_TMP/config"
export AWS_EC2_METADATA_DISABLED=true

read -r -s -p '本机 RGW secret key: ' RGW_SECRET_KEY; printf '\n'
printf '[rgw-lab]\naws_access_key_id = %s\naws_secret_access_key = %s\n' \
  "$RGW_ACCESS_KEY" "$RGW_SECRET_KEY" > "$AWS_SHARED_CREDENTIALS_FILE"
unset RGW_ACCESS_KEY RGW_SECRET_KEY
cat > "$AWS_CONFIG_FILE" <<'EOF'
[profile rgw-lab]
region = us-east-1
s3 =
    addressing_style = path
EOF
chmod 600 "$AWS_SHARED_CREDENTIALS_FILE" "$AWS_CONFIG_FILE"
printf 'synthetic object\n' > "$RGW_TMP/sample.bin"

# 下列 endpoint 和专用 bucket 都必须指向本机选修 RGW；随机名避免碰共享对象。
LAB_BUCKET="m08-lab-${RANDOM}-${RANDOM}"
aws --profile rgw-lab --endpoint-url http://127.0.0.1:7480 \
  --region us-east-1 s3api create-bucket --bucket "$LAB_BUCKET"
aws --profile rgw-lab --endpoint-url http://127.0.0.1:7480 \
  --region us-east-1 s3api put-object --bucket "$LAB_BUCKET" --key sample.bin --body "$RGW_TMP/sample.bin"
aws --profile rgw-lab --endpoint-url http://127.0.0.1:7480 \
  --region us-east-1 s3api head-object --bucket "$LAB_BUCKET" --key sample.bin
# 先确认该 bucket 仅含本练习对象，再显式清理本脚本创建的资源。
aws --profile rgw-lab --endpoint-url http://127.0.0.1:7480 \
  --region us-east-1 s3api delete-object --bucket "$LAB_BUCKET" --key sample.bin
aws --profile rgw-lab --endpoint-url http://127.0.0.1:7480 \
  --region us-east-1 s3api delete-bucket --bucket "$LAB_BUCKET"
```

示例只展示测试形状，不保证每个 RGW 安装的 endpoint/认证配置都相同。测试结束时只删除自己创建的对象/bucket，并先列出资源核对；切勿对共享 RGW 运行递归清理。若没 RGW 环境，跳过即可，不影响 M08 完成。

**版本边界（盘点日期：2026-10-09）：**AWS CLI v2 2.37.11 的选择见课程[版本矩阵](../../课程大纲/版本与实验环境.md)和[上游 release](https://github.com/aws/aws-cli/releases/tag/2.37.11)；Ceph v20.2.4 的 RGW 行为以[该版本 S3 文档](https://docs.ceph.com/en/tentacle/radosgw/s3/)和发行标签为线索。上游 tag/文档并非本课程的集成测试报告。Amazon S3 托管服务端无法固定构建版本；若做 AWS 对照，记录日期、区域、操作列表和账号策略，不要求账号、bucket 或公网服务。

## 7. 常见误区

- **“用了 aws CLI 就是 AWS S3 兼容。”** CLI 只是客户端；服务端可能缺操作、错误语义、签名/header 或权限功能。
- **“SigV4 成功就有权限。”** 签名负责认证请求完整性/身份的一部分，授权策略仍可拒绝请求。
- **“上传 multipart/form-data 就一定是对象分片上传。”** 前者是表单编码；后者有独立会话、part 和 Complete/Abort 操作。
- **“Abort 或客户端超时后资源自动消失。”** 检查 upload ID/parts，设置监控/生命周期兜底；不能假设超时等同取消。
- **“某次 Complete 超时，直接再发 Complete 或 Delete 就行。”** 先检查对象与上传会话状态；避免错误覆盖/删除已提交对象。
- **“ETag 可代替文件 checksum。”** 依产品、加密和 multipart 方式变化；校验使用明确支持的 checksum contract。
- **“Ministore 是本机的 S3 模拟器。”** 它是一个没有网络/认证协议的有限本地对象 API，不是模拟 SigV4 或验证客户端兼容性的服务。
- **“本地 RGW 兼容测试通过，AWS 产品保证也验证了。”** 不能推导；RGW 与托管 S3 是不同实现/运维责任。

## 检查题与作业

1. 画出 CreateMultipartUpload 后上传三片、第二片超时、Complete 响应丢失的状态机。分别说明查询、重试和清理依据。
2. 给图床服务写一个最小权限矩阵：普通上传者、下载者、维护管理员分别允许什么操作？列出不应该授予的管理权限。
3. 如果应用已经在 MySQL 写入 user-file relation，但 multipart Complete 失败，为什么不能用一个对象 API 请求自动回滚数据库？设计一个 reconciliation 状态。
4. MiniStore 超过 1 MiB 拒绝输入，与 S3 multipart 支持大对象有何本质差异？MiniStore 有没有残留 part 要清理？
5. 为一个目标实现设计最小兼容测试矩阵：至少包括 PUT/overwrite/GET/LIST/delete、签名/权限失败、超时重试和未完成 multipart 清理，并标注哪些是产品文档承诺、哪些只是本地观察。
