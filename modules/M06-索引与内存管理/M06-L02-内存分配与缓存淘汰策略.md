# M06-L02：内存分配、缓存淘汰与固定轨迹比较

> 状态：课程正文　｜　建议课时：105–120 分钟（含实验）　｜　先修：[M06-L01：KV 索引结构](M06-L01-KV索引结构与工作负载选择.md)、基本指针/对象生命周期；配套 [IndexCacheLab](../../projects/IndexCacheLab/README.md)。

## 学习目标

学完后你应能：

1. 区分通用堆分配、对象池、arena 与 slab/size class，解释小对象管理、分配器元数据、碎片和生命周期的权衡。
2. 理解固定 slot 空闲链表如何分配/回收，列举对齐、尺寸、归属、双重释放、扩容、线程安全等必需不变量。
3. 描述缓存容量、命中/未命中、LRU 与 FIFO 淘汰状态转移；知道淘汰策略不负责缓存一致性/持久性。
4. 在相同、固定种子的访问轨迹和容量下对照至少两种策略，精确计算命中率并复现校验和。
5. 对合成模拟结果声明版本、工作负载与测量限制，不把命中率或函数运行时间冒充硬件基准。

## 1. 内存分配与对象生命周期

常规 `malloc/new` 把对象生命周期交给通用分配器，适合尺寸/寿命多样的请求，但每对象元数据、对齐、同步和碎片管理会有开销。频繁创建销毁小型索引节点时，可使用专用池或 arena 降低管理成本；设计必须先解决“何时可复用、谁拥有对象、哪些引用还在使用”。

```text
索引插入 ──► 取得 node ──► 链入 hash/tree/skiplist
删除/淘汰 ──► 从结构摘除 ──► 确认无读者引用 ──► 归还 allocator
```

- **Arena / region allocator：**整批分配一段区域，内部 bump-pointer 分配；重置/销毁时整段释放。适合生命周期相近的对象；单个对象通常不能随意独立回收，峰值占用可能保留到整个 region 结束。
- **Slab / 固定尺寸对象池：**预先申请一页或多个 slab，将其中切成同类对象 slot；空闲 slot 用 free list 串起。分配/归还可为 `O(1)`，降低小对象频繁通用分配的成本；尺寸不匹配造成内部碎片，外部页/池仍须向通用分配器申请并回收。
- **Size class：**按多种尺寸等级维护 slab，减少固定单一 slot 的浪费；取整到 size class 仍有内部碎片，并增加池管理/回收策略。
- **通用分配器：**具备复杂的线程缓存、尺寸分类、页回收等实现，实际行为取决于 allocator 与版本。不能根据一段教学 free-list 代码推断 `malloc` 性能，也不能声称自建池一定更快。

### Slab free list 必须满足的不变量

典型 free-list slot 空闲时把 next 指针写在 slot 内；分配时弹出头结点，释放时把它插回空闲链。一个能安全讨论的实现还应验证：

1. `slot_size` 足以容纳指针和对象/头部，并按所存类型正确对齐；每页可用区间与尾部余数有明确规则。
2. 回收地址确实属于该 slab、处在 slot 边界且当前已分配；不能重复释放、越界解引用或破坏链表。
3. slab 管理元数据有可达生命周期；部分满/全满/空 slab 的归属和何时释放整页都明确。
4. 多线程下分配/回收同步；对象被删除后，正在读取的线程不会访问已复用 slot。锁、epoch、hazard pointer 或不可变快照是不同方案，不可混为一谈。
5. 超容量分配、分配失败、初始化失败与池销毁有明确行为；是否触碰 DMA/设备内存需要另行遵循对应 API 规则。

Slab 的页切分、空闲链表和 slot 复用适合说明分配器结构，但实现仍须校验 `block_size`（0、过小、不整除）、指针归属/对齐、双重释放、free_count 上界、扩容与并发。slab 是内存管理策略，不代表数据持久化到 NVMe；Node/value 的磁盘格式和 WAL 属于另一个层次。

## 2. Cache 是副本，不是 allocator

索引 allocator 管对象内存取得/归还；缓存则保存可重建的副本或工作集，以避免更慢层级的读取。缓存系统至少要有 key、内容来源、有效性/版本、容量口径和失效/回填规则。LRU/FIFO 只决定容量不足时“逐出谁”，并不证明保留值仍然正确。

```text
请求 key ──► cache hit ──► 返回已缓存副本
       └──► miss ──► 下层读取/计算 ──► 回填（依一致性协议）
容量超限 ──► replacement policy 选择 victim ──► 回收缓存占用
```

若下层记录被改写，旧缓存副本可能失效；必须通过写穿/写回、版本检查、失效通知、租约/TTL 或访问者约束定义一致性。淘汰旧 entry 不会自动把脏数据写到 WAL/设备；缓存命中也不等于数据已持久化。课程 MiniStore 没有实现这样的 BlockCache 或通用缓存层。

本课对比固定大小的整数 key，容量以“entry 数”计数：不模拟 variable-sized value、缓存字节预算、脏页、预取、并发或缓存层级。命中率定义为同一轨迹中的 `hits / accesses`；冷启动，无预热，命中与 miss 均包含在分母。

## 3. LRU 与 FIFO 状态转移

### LRU：Least Recently Used

缓存命中时把该 key 移到最近使用端；miss 时插入新 key，满时逐出最近最久未被访问的 entry。可用双向链表 + 哈希定位表实现平均 `O(1)` hit/update/evict，但每个 entry 有映射与链表节点开销。每次命中都维护 recency 元数据；高并发系统需要同步或近似策略。

### FIFO：First In, First Out

按进入缓存的顺序排队；hit 不改变顺序；满时逐出最早插入者。队列 + membership 集合可实现平均 `O(1)` 操作，更新逻辑简化，但忽略“近期重新访问”的信息。

策略效果依赖访问模式。以下容量 3 轨迹用来验证规则，而不是总排名：

```text
访问：1, 2, 3, 1, 4, 2
LRU：  1 命中后变最近；访问 4 逐出 2；最后 2 未命中 → 1 hit
FIFO： 1 命中不改变先进顺序；访问 4 逐出 1；最后 2 命中 → 2 hits
```

该结果不说明 FIFO 通常更好。改变尾部为访问 `1`，LRU 这时命中而 FIFO 不命中。真实系统也可能选 Clock/Second-Chance、ARC、TinyLFU、分段 LRU 或按成本/大小加权策略，以缓解 LRU 元数据开销、扫描污染或热点工作集变化。

## 4. 固定种子轨迹与验收口径

自动生成器位于 [`src/index_cache.hpp`](../../projects/IndexCacheLab/src/index_cache.hpp) 的 `make_fixed_trace()`，使用 C++ `std::mt19937` 固定 seed `0x4d3036` 和直接取模映射；没有依赖标准库 `uniform_int_distribution` 的实现细节。固定轨迹参数如下：

- 总访问数 12,000；每 1,000 个请求为一轮；
- 每轮 700 个请求从 24 个热点 key 中抽取，200 个请求访问扫描集合（128 个 key），100 个请求从 256 个 key 的宽集合中抽取；
- cache 容量 32 个 entry，LRU/FIFO 使用同一轨迹，各自冷启动；不预热、不重复采样、不测墙钟时间；
- 轨迹 32-bit key 序列的 little-endian FNV-1a 64-bit 校验和为 `766801a21e475d3a`。代码中校验函数使用 FNV-1a，仅为检测轨迹版本变化，不是密码学签名。

```sh
make -C 'projects/IndexCacheLab' clean test
'projects/IndexCacheLab/build/index_cache_lab' --report
```

已冻结的接受值：

| 策略 | Hits | Misses | Hit rate |
|---|---:|---:|---:|
| LRU | 8,251 | 3,749 | 68.7583% |
| FIFO | 8,243 | 3,757 | 68.6917% |

这些数字是固定代码、seed、轨迹构造和容量下的**确定性功能验收值**。八次命中之差很小，只能说明这条轨迹在该实现上的结果，不能推出 LRU 对任何真实缓存都更好。程序报告编译器版本（编译期宏）、C++ 标准级别、访问数/seed/校验和、entry 容量及计数；`make test` 另外执行策略短轨迹测试、容量为零测试、轨迹复现和 4,000 次索引参考模型比较。

建议报告时只描述：

```text
版本：由程序输出的编译器标识及 C++ 标准级别；记录 git commit 和编译命令
负载：seed=0x4d3036，12,000 次，24-key 热点/128-key 扫描/256-key 宽集合
缓存：32 个固定大小 entry，冷启动；指标 hits、misses、hits/accesses
```

环境中的命令输出可随编译器版本改变；只要固定 seed/算法与 C++ 的 `mt19937` 输出一致，轨迹校验和及命中接受值应不变。若任何值变化，先核对生成器、访问顺序、key 映射或策略语义，不能把差异直接说成性能提升。

## 6. 理论与实现边界 / 禁止过度测量

- 模拟器是单线程、进程内整数 key，LRU 用 `std::list` 与 `std::unordered_map`，FIFO 用 `std::list` 与 `std::unordered_set`；哈希容器本身的渐近/分配行为不计入命中率。
- 每个 cache 项同权同大小；容量是 entry 数，不是 bytes。未测堆分配、fragmentation、RSS、页缓存、设备读写、同步、并发、锁争用、尾延迟或能耗。
- 轨迹为作者定义的合成负载，不是公开生产 trace、Zipf 分布拟合、统计抽样研究或跨工作负载综合评估；扫描/热点比例也不是普适业务模型。
- `mt19937` 的引擎序列由标准规定，映射方式是本程序定义的 `%`；模运算有轻微偏差，但有意追求简单与可复现。seed 固定是实验复现方法，不是生产安全随机策略。
- 不把模拟运行秒数当 benchmark；不跑未受控并发 benchmark，不声称缓存命中率等同 IOPS、吞吐或延迟改善。真实测量必须固定软件/硬件版本、编译选项、线程数、数据集、缓存热度/预热、请求混合、重复次数和统计方法，并先证明缓存语义正确。
- 与 M05 MiniStore 保持分离：项目不接入其 WAL/文件目录/命令路径，也不修改 M05 实现。任何未来集成必须补上 MiniStore 原有 `make clean all test` 回归、恢复语义测试和缓存失效/一致性测试，单有命中率不够。

## 常见误区

- **“Slab 就是缓存或磁盘格式。”** slab 管理对象内存；cache 保存可重建副本；WAL/SSTable 是持久化格式，三者生命周期/正确性完全不同。
- **“每 slot 用指针串 free list 就已是生产 allocator。”** 仍需尺寸、对齐、归属、重复释放、空闲数、线程并发、扩容和 slab 回收规则。
- **“LRU 永远胜 FIFO。”** 淘汰优劣取决于轨迹；扫描型访问甚至可能污染 LRU 工作集。
- **“命中率高意味着服务快/设备写得少。”** 只在明确缓存层级、字节大小、读写成本与命中后路径时才能联系端到端指标。
- **“一次构造 seed 即真实用户 workload。”** 可复现不等于代表性；需要先有来源与适用场景。
- **“缓存命中就是持久化成功。”** 缓存副本可存在于易失内存，且可能过期；确认点取决于系统持久化协议。

## 检查题

1. 为什么固定单尺寸 slab 会产生内部碎片？若一个节点尺寸接近两个 size class 边界，如何选择池策略？
2. free-list 只要维护 `first_free` 和 `free_count` 是否能防止 double-free？还缺哪些信息/校验？
3. 对容量 3 的 `1,2,3,1,4,2`，按规则推演 FIFO 与 LRU；为何改变最后一个请求可能翻转结果？
4. 为什么缓存 hit rate 的分子/分母必须对应相同请求集合？读取对象大小变化会怎样影响“按请求”与“按字节”命中率？
5. 若缓存数据被其他进程写入，LRU/FIFO 能否发现陈旧副本？需要何种失效协议？
6. 要把这条离线模拟变成可以对真实软件作性能判断的实验，还必须固定哪些环境、测量边界、重复和统计条件？
