# M06-L01：KV 索引结构与工作负载选择

> 状态：课程正文　｜　建议课时：100–115 分钟　｜　先修：[M05-L01：KV API 与本地持久化数据路径](../M05-本地KV引擎/M05-L01-KV-API与本地持久化数据路径.md)、基本算法复杂度。配套程序：[IndexCacheLab](../../projects/IndexCacheLab/README.md)，C++20。

## 学习目标

学完后你应能：

1. 分辨哈希表、跳表、平衡搜索树、B/B+ 树与 Radix/Trie 的结构和操作复杂度，并说清平均/期望界限与最坏界限的差别。
2. 依据点查、更新、精确范围扫描、前缀查找、内存容量及持久化介质选择索引，不以单个“大 O”结论替代工作负载分析。
3. 解释重哈希、平衡修复、跳表随机层高、节点指针/allocator 成本，以及范围访问对键顺序的要求。
4. 用一个共同 API 验证三种内存索引的 put/upsert、get、erase 和半开范围查询结果一致。
5. 分清教学模型、标准库接口保证与某个数据库/产品的具体实现；指出并发访问必须有明确同步与对象生命周期方案。

## 1. 索引不是数据本身

KV 引擎至少要回答“key 当前映射到哪个 value/版本/位置”。索引可以保存 value，也可以保存指向记录、页、SSTable 或日志位置的指针。更改索引实现不会自动改变 API 一致性、WAL 持久化、删除墓碑或并发保证。

```text
put(key,value) ──► 索引更新 / 指针定位 ──► 记录或内存对象
get(key)       ──► 索引查找 ────────────► value / 未命中
range(a,b)     ──► lower_bound(a) ──────► 按序读取至 b
```

在 M05 MiniStore 中，内存 `std::map` 用于已恢复状态与排序列举；它不是直接写到每次请求访问的磁盘索引。LSM MemTable 常用跳表、平衡树或其他有序结构；SSTable 则可用块索引与 Bloom filter 降低磁盘查找成本。Bloom filter 可判定“不可能存在”，不能给出 value，也不能解决版本选择。

以下复杂度以 `N` 个不同 key、通常均摊节点操作为口径；不包含 key/value 字节长度、内存分配、缓存 miss、锁竞争和底层 IO。`K` 是范围查询返回的元素数。字符串比较本身可能与 key 长度相关。

## 2. 哈希表：精确点查与无序键

### 2.1 结构与操作

桶数组将 key 的哈希值映射到桶；冲突可以用链地址（每桶保存节点集合）或开放寻址（在连续槽位探测）处理。链地址插入时必须更新真正的桶头，而不是只改局部指针。装载因子 `α = N / bucket_count` 影响冲突与内存利用率。动态表超过阈值时重哈希：单次重哈希为 `O(N)`，合理扩容策略下连续插入通常有均摊分析。

| 操作 | 常见平均/期望复杂度 | 最坏复杂度 | 关键条件 |
|---|---:|---:|---|
| 精确 get / put / erase | `O(1)` | `O(N)` | 哈希分布良好、冲突处理、负载因子受控；重哈希单次 `O(N)` |
| 无序遍历全部记录 | `O(N)` | `O(N)` | 遍历桶和节点 |
| 有序范围 `[a,b)` | 没有天然次序 | 通常至少扫描 `O(N)`；示例还排序匹配项 | 需另加有序索引或对结果排序 |

“平均 O(1)”是依赖散列质量/输入假设的描述，不是每个 key 必然常数时间。按字节求和再取模的简单散列会抹掉输入顺序，许多排列都会碰撞；简单散列也可能被刻意制造的碰撞拖垮。IndexCacheLab 用 FNV-1a 只作可复现实验中的非密码学哈希示例；它不防 HashDoS，也不承诺安全散列。

适合：大量独立精确查找、没有自然排序要求、能接受碰撞/重哈希管理的内存映射。若业务需要稳定按 key 列举、前缀或范围，哈希表可能要与另一套有序索引并存，带来额外内存和更新一致性负担。

## 3. 跳表：有序链表的多层捷径

最低层保存全部节点并按 key 排序；向上各层是更稀疏的快捷链。查找从高层向前移动，直到下一 key 不小于目标，再下降一层。插入先记录各层前驱，再为新节点抽取层高并更新链接；删除同样更新受影响的前驱。

| 操作 | 期望复杂度 | 最坏复杂度 | 特性 |
|---|---:|---:|---|
| get / put / erase | `O(log N)` | `O(N)` | 几何随机层高带来期望平衡，不是严格最坏界限 |
| 有序范围 `[a,b)` | `O(log N + K)` | `O(N + K)` | 找到起点后可沿底层链表顺序扫描 |
| 空间 | `O(N)` | 层高上限限制每节点额外指针 | 随机层数、指针和 allocator 产生开销 |

跳表层高分布是期望复杂度来源。固定 seed 适合自动测试复现，但生产级随机数/确定性威胁模型与教学 RNG 不同。删除层高、内存回收与并发读者交互也并非“链表操作所以天然安全”。在 M05 的多版本/并发引擎里，还需结合快照、迭代器、写入锁和节点生命周期设计。

## 4. 平衡搜索树与其他有序结构

平衡二叉搜索树（如 AVL 或红黑树）通过旋转/颜色或高度不变量限制树高，支持 `O(log N)` 搜索、插入、删除与 `lower_bound`，有序范围遍历为 `O(log N + K)`。它适合需要有序迭代、范围查找并希望有确定高度界限的内存索引；每个节点仍需 key/value 或指针、父子关系、平衡元数据，节点分散分配可能导致 cache miss。

本项目的 `TreeIndex` 用 C++ `std::map` 作为标准有序树接口模型：标准对查找/插入/删除给出对数复杂度要求，但不规定底层必须是红黑树。很多常见标准库实现选择红黑树；不能把它写成 C++ 标准保证，也不能把容器行为推广为某一数据库索引。

| 结构 | 典型访问 | 主要取舍 |
|---|---|---|
| AVL / 红黑树 | 内存点查、更新、有序迭代、范围 | 二叉高度较大但边界可控；节点指针跳转多，更新需旋转/重着色 |
| B-tree / B+ tree | 大型索引、页/块存储、数据库范围扫描 | 高扇出降低树高和页访问数；节点/页布局、分裂合并、缓存和持久化更复杂；B+ 常把记录放叶子且叶间有序链接 |
| Radix tree / Trie | 前缀、字节/位前缀或整数索引 | 可能利用公共前缀快速定位；空间与实现取决于压缩方式和 key 字母表，不是所有 key 都更省 |

磁盘 B+ 树常以“访问多少索引页/数据页”分析，而不是只数 CPU 比较次数；扇出 `B` 大时树高可接近 `O(log_B N)`。内存 cache 命中后模型又不同。若 workload 是范围扫描，连续叶页布局和顺序 IO 的收益可能比点查平均比较数更重要。若 key 都很短且热点集中，哈希/树节点布局、allocator、硬件缓存同样可能改变实际开销。

### 选择时问的问题

1. 是精确点查还是范围/前缀查询？结果是否必须按 key 排序？
2. key 是否可信、分布如何、写入会否频繁扩容或大量删除？是否有最坏延迟要求？
3. 数据常驻 RAM，还是索引页可能进入 SSD？是否可以用多份索引换取查询能力？
4. 对象/节点如何分配和回收？读者持有指针时何时能释放？需不需要锁、RCU、epoch 或版本快照？
5. 索引对 WAL、MemTable、SSTable 的职责边界是什么？错误/未命中如何表达？

没有一种结构在所有负载下占优。复杂度表是指导建模，不是性能排名，也没有包含序列化、复制、缓存、锁和 IO。

## 5. IndexCacheLab：共同 API 的功能验收

程序源码：[索引与缓存实现](../../projects/IndexCacheLab/src/index_cache.hpp)、[报告入口](../../projects/IndexCacheLab/src/main.cpp)、[自动测试](../../projects/IndexCacheLab/tests/test_index_cache.cpp)。构建器是 C++20 `g++`/兼容编译器，不依赖第三方库。

```sh
make -C 'projects/IndexCacheLab' clean test
'projects/IndexCacheLab/build/index_cache_lab' --report
```

API 统一为 `put`（同 key 覆盖）、`get`（返回可选值）、`erase`（报告是否存在）、`range(lower, upper)`（半开区间，升序）。程序中的三个结构是：分桶链地址哈希、最高 16 层的简化跳表和 `std::map` 有序树。它们只存内存字符串、不持久化、不并发。

自动测试用固定 LCG 种子 `0x4d3036` 执行 4,000 次插入/覆盖/查找/删除，与 `std::map` 参考模型比较；然后检查全部 live key 以及范围结果。主程序另用 1,024 条固定 key 验证三种索引点查及 20 条范围结果。预期摘要：

```text
index_workload: entries=1024 puts=1024 point_gets=1024 range=[k000100,k000120) matches=20 correctness=PASS ...
```

这个路径不计时、不报告吞吐或延迟；其用途是语义相同的功能验收。哈希版本的范围查询必须扫描全部桶并排序结果，因而不可用它的点查平均复杂度推导范围性能。

## 6. 理论与实现边界

- 教学 skiplist 以固定 seed 生成层级，最高 16 层；真实实现还要定义熵来源、并发更新、内存回收和最大容量。
- `HashIndex` 有动态扩桶，但没有抗恶意输入的 keyed hash、资源限额或持久化格式。FNV-1a 不是安全哈希。
- `TreeIndex` 借助 `std::map`，不手写红黑树；C++ 标准不承诺内部节点布局或具体树种。
- 所有索引无锁保护。多线程同时 put/get/erase 不是安全用法；旧讲义“get 只读所以不必加锁”的推断错误：并发结构改动会产生数据竞争、悬空指针或未定义行为。若用读写锁，也必须覆盖节点被删除/释放的生命周期。
- `range` 返回复制出的 vector，计入额外 `O(K)` 内存；不是数据库游标、快照或零拷贝迭代器。
- “索引复杂度”没有覆盖键长、value 大小、节点分配、CPU cache、页表、NUMA、allocator 碎片、同步、持久化及设备访问。

## 常见误区

- **“哈希表永远 O(1)。”** 仅是负载与散列假设下的平均/均摊描述；单桶碰撞会达到线性。
- **“跳表像 B+ 树，所以访问特性相同。”** 两者都有多层有序导航的直观类比，但节点扇出、页布局、持久化和复杂度/实现细节不同。
- **“树索引自动适合 SSD。”** 二叉树节点散布会导致随机小访问；磁盘 B/B+ 树通过高扇出/块布局优化 IO，不能只因都叫树就等同。
- **“只读 get 不需要同步。”** 只有在明确安全的并发实现/不可变快照下才可能成立；普通 C++ 容器并发读写未同步不安全。
- **“索引选对即得到 WAL/LSM 正确性。”** 索引是易失查询结构；持久化、恢复顺序、墓碑和版本规则另有约束。

## 检查题

1. 对 1,000 万 key 的精确随机查找与有序前缀扫描，哈希表、跳表和 B+ 树分别有什么优缺点？哪些成本没在复杂度表里？
2. 为什么哈希 rehash 的单次成本高仍可能适合高频 put？均摊结论依赖什么增长策略？
3. 随机跳表的“期望 `O(log N)`”和红黑树的“最坏 `O(log N)`”有何本质区别？
4. `std::map` 的接口保证能否证明底层一定是红黑树？
5. 已恢复的 M05 map 与磁盘 SSTable 索引是什么关系？Bloom filter 能否直接返回 value？
6. 索引 API 返回内部 value 指针时，若另一个线程更新/删除节点，调用方会遇到什么生命周期问题？
