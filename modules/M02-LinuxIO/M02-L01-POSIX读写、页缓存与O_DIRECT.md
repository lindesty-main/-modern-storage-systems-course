# M02-L01：POSIX `read`/`write`、页缓存与 `O_DIRECT`

> 状态：正文完成　｜　建议课时：100–110 分钟　｜　适用范围：Linux 普通文件与本地 socket；M02 必做实验只使用程序自行创建的临时普通文件和 `socketpair`，不访问设备节点、不需要 root。

## 学习目标

学完后，你应能：

1. 区分文件描述符、当前文件偏移和显式字节偏移，正确选择 `read`/`write` 或 `pread`/`pwrite`。
2. 为短读、短写、`EINTR`、EOF 和错误编写正确的循环；知道 socket 的返回语义与普通文件略有不同。
3. 解释普通文件读写与页缓存、回写和文件系统的关系，并区分系统调用完成与持久化。
4. 说明 `O_DIRECT` 试图改变哪一段数据路径、有哪些对齐/兼容限制，以及它不意味着什么。
5. 在受控普通临时文件上运行 [Lab 03](../../labs/lab-03-linux-io/README.md)，说明测试结果不等同于设备性能或掉电保证。

## 先修与问题场景

先修：Linux 命令行、C 指针与 `size_t`、文件描述符概念。无需 NVMe、裸盘、fio 或管理员权限。

程序要读取一个文件区间时，表面调用很简单：`read(fd, buf, len)`。困难在于：返回值可能小于 `len`，`read` 可能推进共享文件偏移，普通文件数据通常和页缓存交互，而“调用成功”并不自动等于“数据已到持久介质”。若为了“绕过缓存”加入 `O_DIRECT`，又会遇到内存地址、长度、偏移对齐和文件系统差异。先理解 API 合约，再讨论某种路径是否适合工作负载。

## 普通文件的路径与缓存

```text
应用缓冲区
   │ read/write 或 pread/pwrite（文件描述符、字节长度/偏移）
   ▼
系统调用 → VFS → 文件系统
                 ├─ 通常经页缓存：缓存命中可直接复制；未命中会填充缓存
                 └─ 写入常先修改页缓存中的页，随后由回写机制下发
   ▼
块层 / 驱动 / 设备
   │ 完成后逐层返回；写回与持久化还受同步请求、设备缓存等影响
   └──────────────────────────────────────────────────────────────
```

图中是常见 Linux 普通文件路径，不表示每次 `read` 都触发物理设备请求。**页缓存**（page cache）缓存文件内容，并由内核管理回读、预读、脏页和回写。读请求可能完全命中缓存；写请求可能先在缓存中变成脏页，之后由内核写回。VFS/文件系统还管理命名、权限、元数据和文件到块的映射；普通文件 API 不直接暴露设备 LBA。

页缓存使常见访问更快，但也会影响观测：重复读同一文件可能由内存服务；短时写吞吐可能主要反映脏页接收速度；缓存压力、预读、并发回写和后台活动会改变延迟。用普通文件做练习适合验证 API 与正确性，不适合据此宣称硬件 IOPS、介质延迟或耐久性。

## `read`/`write` 与 `pread`/`pwrite`

`read(fd, buf, count)` 从当前文件偏移开始读取，成功时返回实际读到的字节数并推进该 open file description 的偏移。`write` 类似地从当前偏移写入并推进偏移。通过 `dup` 或继承得到的描述符可能共享同一个 open file description，因此共享偏移会成为并发代码的竞态来源。

`pread(fd, buf, count, offset)` 与 `pwrite` 使用显式的**字节偏移**，不会改变当前文件偏移；这让多个工作线程可以并行处理不重叠区间，而不需要围绕 `lseek` 加锁。偏移仍需合法，长度与加法应避免溢出。Linux 上 `pwrite` 与 `O_APPEND` 同用有历史行为偏差：即使给了显式偏移仍可能追加；需依照目标系统文档，避免把这对标志组合当成可移植定位写。

### 返回值不是“必定处理完请求”

- 正数 `n`：本次成功处理 `n` 字节，通常 `0 < n <= count`。剩余部分由调用方继续处理。
- 普通文件 `read` 返回 0：到达当前 EOF；socket `read` 返回 0 通常表示对端有序关闭写方向。不能把二者的 0 都解释成相同应用事件。
- `-1`：检查 `errno`。`EINTR` 表示信号中断；若没有字节传输可重试。非阻塞描述符暂时无进展可能返回 `EAGAIN`/`EWOULDBLOCK`，此时应等待就绪或安排重试，不能忙循环。
- `write` 到 socket 时还要考虑 `SIGPIPE`/`EPIPE`；本实验使用本地 `socketpair`、小消息并检查所有返回值。

完整传输 helper 的核心是：累计正向进展、遇到 `EINTR` 重试、零进展按场景解释、其他错误保留 errno。不要用 `strlen` 推算任意二进制缓冲区的长度，也不要假定读入数据有 `\0` 结尾。

```c
size_t done = 0;
while (done < length) {
    ssize_t n = pread(fd, (char *)buffer + done, length - done,
                      offset + (off_t)done);
    if (n > 0) { done += (size_t)n; continue; }
    if (n < 0 && errno == EINTR) continue;
    if (n == 0) { /* 对固定长度普通文件读取：意外 EOF */ }
    /* 其余情况记录 errno 并退出 */
}
```

示例省略了 `offset + done` 溢出、空指针、`SSIZE_MAX` 和应用层失败清理；Lab 03 的 C helper 对这些教学边界作了显式校验。实际项目还需按 API 语义区分普通文件、socket、设备及非阻塞模式。

## 写成功、同步与持久化边界

`write`/`pwrite` 返回成功表示内核接受并处理了该次系统调用的字节范围，不单独承诺断电后数据一定可恢复。对普通文件，数据可能仍在页缓存。`fdatasync(fd)` 请求同步文件数据及读取这些数据所必需的元数据；`fsync(fd)` 还覆盖相关文件元数据。`O_DSYNC`、`O_SYNC` 可以改变每次写调用的同步要求，但代价取决于实现和设备。

同步系统调用也不是超越整个存储栈的魔法：最终承诺仍受文件系统、块层、设备写缓存、flush/FUA 实现和硬件诚实性约束。新建文件时，文件内容同步不必然保证父目录项在崩溃后存在；有此需求时还要按平台语义同步父目录。Lab 的 `fdatasync` 只验证返回错误是否被处理，不进行断电注入，也不证明真实设备持久性。`close` 不是 `fsync` 的替代品。

## `O_DIRECT`：一种有条件的数据路径选择

在 Linux 上，`open(..., O_DIRECT)` 请求尽量减少文件数据通过页缓存的影响，使文件数据缓冲区以受约束的方式参与 I/O。它仍然是文件描述符上的文件系统 I/O：文件系统、权限、元数据缓存、块层和驱动并未凭空消失。它不等同于访问裸盘，不保证内存到设备“零拷贝”，也不自动提供同步持久化。

最重要的工程要求是**对齐**：缓冲区地址、文件偏移和 I/O 长度都可能需要满足文件系统/设备要求。具体粒度并非所有文件系统、内核和文件都固定为 512 B 或 4096 B。Linux `statx` 自 Linux 6.1 起可在支持的文件系统上通过 `STATX_DIOALIGN` 返回 direct-I/O 内存/偏移对齐信息；老内核或文件系统可能不提供该信息，须查询目标环境文档。`posix_memalign` 只保证所请求的内存地址对齐，不会自动让任意偏移、长度和文件系统条件都合法。未对齐请求可能报 `EINVAL`，部分实现也可能采用其他处理路径，不能假设一致。

对同一文件混用 buffered I/O 与 direct I/O，尤其在并发访问时，须遵循文件系统文档的缓存一致性限制；不要在两路写同时覆盖同一区域。小型随机 I/O、低队列深度或缓存命中工作负载可能并不会因 `O_DIRECT` 变快；禁用页缓存也会失去其好处。正确做法是先明确工作负载和持久性要求，再验证目标内核/文件系统上的对齐和语义。

Lab 03 的 `O_DIRECT` 子测试只在程序自行创建的临时普通文件上尝试 4096 对齐的一页读。系统或文件系统不支持该操作时显示 `SKIP`，不作为整个实验失败；它不比较速度、不操作设备节点，也不把 4096 宣称为所有环境的通用对齐。

## 接口语义与基准边界

比较同步 API 与 `io_uring` 时，必须先固定 direct/buffered、缓存状态、同步策略、队列深度、访问模式和完成语义；否则 IOPS 数字不能作为当前机器或通用结论。`write` 返回与 `fsync` 也不是“未成功/已落盘”的简单二分：同步承诺须结合文件系统、设备语义解释，目录项持久性是另一问题。

单次大文件读写耗时若缺少机器、缓存、数据源、重复次数和剖析证据，不能据此得出“改异步读就是方案”。首先测明瓶颈在存储、CPU、内存复制、调度还是应用处理，再比较 API。

## 常见误区

- **“一次 `read` 会填满 buffer。”** 错；检查返回字节数并按场景循环。
- **“`pread` 只是 `lseek` 后再 `read`。”** 两次调用会改变共享偏移，且有竞态；`pread` 是单次带偏移的接口。
- **“`write` 返回成功就等于持久化。”** 错；缓存、同步、文件系统、设备缓存与目录项边界都要分开讨论。
- **“`O_DIRECT` 就是绕过内核/直接访问盘。”** 错；它针对文件数据路径的页缓存使用，有对齐和文件系统条件，仍经内核文件系统/块层。
- **“页缓存只影响写。”** 错；读命中、预读、回写和内存压力都会改变测得的读写行为。
- **“`O_DIRECT` 就一定更快。”** 错；它改变缓存策略，不替代负载测量，也不会自动增加并发或持久性。

## 课后检查

1. 对普通文件连续 `read` 两次与用 `pread` 读取同一偏移两次，文件偏移有什么差异？若两个线程共享 `dup` 得到的 fd，会发生什么？
2. `read` 返回 4096，而请求 8192 字节，列出至少三种可能原因。若在 socket 上返回 0，和普通文件 EOF 有何不同？
3. 为何 `O_DIRECT` 读取 4 KiB 时，仅仅把 `malloc` 换成 `posix_memalign(...,4096,...)` 仍不足以证明请求合法？
4. 设计一组可以比较 buffered 与 direct I/O 的实验控制变量，并解释为什么重复读同一文件会改变结论。
5. 某程序在写临时文件后 `fdatasync` 成功，崩溃重启时文件名不存在。哪一层语义没有被该调用单独保证？
