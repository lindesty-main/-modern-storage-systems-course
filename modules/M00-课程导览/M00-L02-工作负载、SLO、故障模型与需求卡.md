# M00-L02：工作负载、SLO、故障模型与需求卡

> 状态：课程正文　｜　建议课时：110–120 分钟（含本地练习）　｜　先修：完成 [M00-L01](M00-L01-存储全景与端到端数据路径.md)，会使用 Python 3 和 shell。无需安装第三方包、root 权限、真实设备或外部服务。实验配套：[lab-00-storage-requirements](../../labs/lab-00-storage-requirements/README.md)。

## 学习目标

学完本课后，你应能：

1. 把“应用要快、可靠、便宜”改写成可测量、带边界的工作负载描述和 SLO。
2. 区分吞吐、IOPS、响应时间分位数、可用性、持久性、RPO/RTO、一致性与备份恢复目标。
3. 声明系统要面对的故障、明确排除项、共同原因风险和恢复假设；不把“有副本”直接当成备份或 HA。
4. 使用本地只读自检核对实验环境，并填写、校验一张存储需求卡。
5. 识别需求卡校验器能保证什么、不能替代什么，不把格式通过误报为技术选型或性能验收通过。

## 1. 先描述工作负载，而不是先选产品

工作负载是某段时间内系统真正要处理的请求以及请求之间的关系。只写“对象很多”“随机读”“高并发”不能据此估算容量、性能或容错需求。至少要把以下维度写清楚，并区分已测量、估算和待确认：

| 维度 | 建议描述 | 为什么影响设计/实验 |
|---|---|---|
| 操作构成 | 读/写/覆盖/删除/列表等比例；说明比例按**操作数**还是按字节统计 | 90% 小读 + 10% 大写与按字节 90% 读不是同一种负载；更新和删除可能还要改元数据/日志 |
| 请求大小 | 均值、分位数或大小直方图；对象/键/文件大小分布 | 相同 IOPS 下，大请求的字节吞吐不同；小请求可能由元数据/协议开销主导 |
| 访问局部性 | 顺序/随机、热点比例、工作集大小、冷热数据比例、重复访问间隔 | 缓存、索引和预取受工作集及热点影响；“随机”不说明整个数据集都均匀访问 |
| 并发与队列 | 客户端数、每客户端并发、队列深度、同步/异步、事务范围 | 排队会改变延迟；并发提高可能让吞吐上升也可能造成饱和/尾延迟恶化 |
| 时间变化 | 平均/峰值到达率、突发时长、日/周周期、后台维护窗口 | 短时峰值、压实/备份、恢复流量可能和前台 IO 竞争资源 |
| 数据生命周期 | 初始容量、增长率、保留期、删除/覆盖比例、版本数 | 逻辑容量不等于物理容量；副本、校验、索引、日志、碎片和保留版本都会增加空间 |
| 语义 | 原子写入范围、并发覆盖、读后写可见性、排序/事务、重试幂等性 | 不同 API 即使吞吐相似，也可能提供不同正确性保证 |
| 客户端与网络 | 单机/多客户端、地域、连接复用、协议、重试与超时 | 网络路径、客户端缓存和重试都会改变端到端测量及重复执行风险 |

工作负载要有观测窗口和阶段。把峰值拆成“突发持续多少秒”“突发后多久恢复”比只保留一个峰值数字更有用。请求大小最好保存直方图或 p50/p95/p99，而不是只给均值。读写比也要说明分母：本课的需求卡按**操作数**记录 read/write 百分比，并另设每次请求字节数作为简化代表值；这不足以描述真实请求大小分布。

容量估算要分开逻辑数据与实现开销。一个粗略的逻辑保留量估算可以从“初始数据 + 每日净增长 × 保留天数”开始，但实际物理空间还需计入副本/纠删码、元数据、索引、WAL、临时文件、空间回收滞后、版本和安全余量。不能把该粗算式当作磁盘采购规格或产品容量保证。

**例：**“每天约 8 GiB 新图片”还未说明是净新增还是含覆盖；对象是否有缩略图副本、纠删码、旧版本和过期清理？增长率是高峰月的日均值还是全年均值？如果需求方说“读多写少”，还要追问按次数还是按流量计。需求未确认时，将其放到 `open_questions`，不要悄悄填成精确事实。

## 2. 从目标写成 SLI/SLO

- **SLI（Service Level Indicator）**：对实际服务表现的量化指标，例如合格请求的成功比例或端到端响应时间。
- **SLO（Service Level Objective）**：在给定范围和统计窗口内希望达到的目标，例如“过去 30 天符合条件的读取请求至少 99.9% 在 50 ms 内成功”。
- **SLA（Service Level Agreement）**：面向客户/合同的承诺及其后果。课堂 SLO 草案不是合同，也不自动构成供应商承诺。

一个有用的 SLO 句子至少包含：**对象/请求范围、测量起止点、统计窗口、阈值、失败/重试是否计入、分位数或合格率**。例如“p99 < 40 ms”仍须明确客户端还是服务器端计时、成功请求还是所有请求、峰值还是全时段、冷缓存还是热缓存、请求大小/地区/并发和观测窗口。只测进程内函数时间可能遗漏网络、SDK 重试和队列等待；只看服务端指标也可能看不到客户端连接失败。

### 性能指标不能互相替代

- **吞吐量**：单位时间完成的操作数或字节数。写成 req/s、IOPS、MiB/s 时需定义操作/字节计数口径。若操作大小固定，`IOPS × 每次字节数` 可估算数据字节率；有多种尺寸时应使用实际字节数分布，不把协议开销算成有效载荷。
- **响应时间/延迟**：一个请求从定义的起点到终点所耗时间。平均值会掩盖慢请求；p50/p95/p99 描述分布的不同位置，最大值对样本数和偶发事件敏感。分位数的算法和统计窗口也要固定。
- **并发与队列**：到达速率超过可服务能力时，队列通常增长，尾延迟会先恶化；单看平均吞吐无法说明系统距饱和多远。基准应同时记录负载发生器是否已饱和或自身成瓶颈。
- **资源使用**：CPU、内存、网络、存储容量、后台任务和队列深度可解释结果，但资源值本身不是用户 SLO。

百分位需要足够且具代表性的样本。测 20 个请求并报告 p99，不足以可靠刻画长尾；要报告样本数、重复次数、预热/缓存状态和测量时长。不同工具对分位数的估算方式可能不同。本文没有规定跨工具统一算法，实验报告须明确使用的工具和口径。不要只挑选最好的单次结果。

### 可用性、耐久性与一致性是不同问题

**可用性**通常问：在定义时间/请求集合中，有多少请求成功并满足时限？分母是否包含客户端无法连接、被限流、超时和错误结果，必须写清。99.9% 不是“绝不宕机”，也不说明数据是否安全。

**持久性/耐久性**问：已确认写入的数据在某类故障后仍可恢复的目标/概率/边界是什么？不能仅凭“副本数为 3”推导一个固定耐久性数字；副本位置、确认规则、相关故障和损坏传播都重要。

**一致性**问：并发读写、覆盖、复制延迟或故障恢复时，客户端可观察到哪些值/顺序？“强一致”须落到具体读写模型、键/对象范围和产品实现；不要把缓存一致性、文件原子重命名、数据库事务、线性一致性混为一个标签。

**RPO（Recovery Point Objective）**是某一故障场景下能接受的数据回退/丢失时间范围；**RTO（Recovery Time Objective）**是该场景下恢复到可接受服务的时间目标。两者都要绑定故障等级、起点、数据集和测量方法。RPO=0 是很强的目标，只有明确的同步/确认和故障假设支持时才能成立；RTO 也不能忽略检测、审批、恢复数据量、重建和验证时间。目标不是已达成证据。

## 3. 把故障模型写成明确假设

故障模型不是把“服务器会坏”写进文档就结束，而是声明系统设计和实验要覆盖哪些事件、哪些不覆盖、如何发现故障、允许什么数据/服务结果。按层列清单：

| 故障范围 | 示例 | 需要追问/验证 |
|---|---|---|
| 应用/进程 | 崩溃、强杀、升级回滚、内存耗尽 | 写到一半退出后文件/日志是什么状态？自动重启会否重复请求？ |
| 介质/设备 | 读写错误、设备掉线、静默损坏、容量耗尽 | 错误是否上报、校验在哪里、降级是否可写、如何替换/重建？ |
| 主机/机架 | 主机断电、控制器/主板故障、机架供电问题 | 数据和副本是否跨独立主机/故障域？元数据/控制面是否仍可用？ |
| 网络 | 丢包、延迟、分区、DNS/认证服务故障 | 超时后调用者能否判断写是否已提交？重试如何避免重复？ |
| 软件/操作 | 错误发布、误删、配置错误、密钥泄露 | 版本回滚、最小权限、不可变备份、审计和恢复演练是否存在？ |
| 站点/供应链 | 机房不可达、账号/控制面被攻陷、共同缺陷 | 备份是否有独立凭据/故障域？哪些超出本课程必做范围？ |

分布式系统还需说明故障类型。**崩溃故障**常指节点停止或重启；**遗漏/延迟/分区**是消息未到、迟到或网络两边无法通信；**相关故障**可能同时影响多个副本，例如同一电源、机架、软件版本或误操作。除非明确研究拜占庭/恶意节点，课程普通存储需求卡不把“任意恶意节点发送任意消息”作为默认故障假设，但安全与权限仍需写入约束。

副本提高某些故障下的可用性/可恢复性，但**不是备份的同义词**：复制会迅速传播误删、逻辑损坏或勒索写入；同主机副本无法抵御整机损坏；同步复制也可能复制错误数据。备份需要有恢复点、保留策略、独立访问/故障域和定期恢复演练。校验和可以帮助发现某些损坏，但不能自己恢复丢失数据。

选择性故障模型是设计边界，不是安全保证。若把站点整体毁损列为不覆盖项，仍应在业务风险记录中清楚批准该取舍；不能在总结里把“不测试”写成“不会发生”。对每个重点故障，最好写出：触发条件、检测信号、处理动作、预期可用性/数据结果、恢复时间和验证证据。

## 4. 实验环境也是需求的一部分

不同机器/依赖可能改变命令可用性、内核 API 和结果。课程规划提出的主线候选为 Ubuntu Server 24.04.5 amd64、GA Linux 6.8.0-146.146、GCC 13/CMake 3.28；[版本与实验环境](../../课程大纲/版本与实验环境.md)明确这是候选组合，需要发布前集成验证，不是任何人机器都符合的硬性要求，也不是已完成认证。

本课实验故意不编译内核模块、不挂载文件系统、不访问 `/dev`、不安装包、不启动网络服务、不调用 `sudo`。本地自检仅读取 Python/OS/内核信息并检查工具是否在 `PATH`；需求卡校验器只读取 JSON。自动测试会在操作系统创建的临时目录里写入小型测试文件，退出时由测试框架清理。除本地 Python 3 外不需要第三方依赖。实验要记录 `python3 --version`、`uname -a`、`gcc --version`（如存在）等，不应将“检查通过”解释为候选环境集成测试。

可复现报告还要记录：代码/脚本版本、主机/虚拟机、OS 和内核、工具版本、工作负载、种子/数据集、缓存状态、执行命令、测试次数和结果。M00 的实验不跑性能测试，因此只能形成需求和环境记录，不能宣称实际吞吐、IOPS、持久性或可用性达标。

## 5. 本地实验：环境自检与需求卡

实验目录：[lab-00-storage-requirements](../../labs/lab-00-storage-requirements/README.md)。所有命令只作用于课程仓库和你创建的临时目录。先阅读 lab README 中的安全边界和 schema。

### 步骤 A：只读环境自检

```sh
cd labs/lab-00-storage-requirements
python3 -B m00_preflight.py check
python3 -B m00_preflight.py check --json
python3 --version
uname -a
command -v gcc >/dev/null && gcc --version || true
```

程序会报告 Python、OS 标识、架构、内核 release 和 gcc/make/cmake/git/fio 是否可找到，并把 Ubuntu 24.04 系列与 amd64 作为**候选基线对照**。它不会自行判失败：不同发行版可完成本地课程实验；`uname` 也不能单独证明发行版内核包修订号。手动命令只查看版本，不安装/运行 IO 基准。检查的结果不是安全扫描或兼容性认证。

### 步骤 B：验证虚构样例

```sh
python3 -B m00_preflight.py validate requirement-card.example.json
PYTHONDONTWRITEBYTECODE=1 python3 -B -m unittest -v test_m00_preflight.py
```

样例描述一项**完全虚构**的缩略图服务需求。校验器预期输出 `VALID`；自动测试覆盖样例、读写比例和为 100 的约束、百分比/时延边界、故障范围/候选方案完整性、JSON CLI 失败不改源文件，以及自检不写当前工作目录。

### 步骤 C：填写自己的需求副本

在实验目录执行下列命令。`mktemp` 建立一个随机私有目录；`cp` 只把已提供样例复制到这个新目录。编辑 `card.json`，不要修改仓库里的示例文件。终端结束时仅删除本次创建的临时目录。

```sh
set -eu
TMP_DIR=$(mktemp -d "${TMPDIR:-/tmp}/m00-card.XXXXXX")
trap 'rm -rf -- "$TMP_DIR"' EXIT
trap 'exit 1' HUP INT TERM
cp requirement-card.example.json "$TMP_DIR/card.json"
"${EDITOR:-vi}" "$TMP_DIR/card.json"
python3 -B m00_preflight.py validate "$TMP_DIR/card.json"
```

如果没有图形编辑器，可用系统已有的文本编辑器；不要把 `TMP_DIR` 换成 `$HOME`、系统目录或已有数据目录。校验器会拒绝符号链接、非普通文件和超过 1 MiB 的 JSON，以避免把文件系统对象误当需求文件；它不执行 JSON 内容。按 lab README 中的字段说明完成以下改动：

1. 把服务名和数据敏感级别改成自己的练习场景；填写初始容量、日增长和保留期的单位。
2. 写出按操作数计算的读/写百分比且合计 100；明确请求字节数是代表值、访问模式、工作集、峰值操作数、并发和突发时间。
3. 写一个有测量窗口的 SLO 草案；将目标阈值和实际测量结果区分开。若指标含义还不清楚，补到 `open_questions`。
4. 至少列一个纳入和一个排除的故障，并给出假设；填写一致性、耐久性、RPO/RTO。RPO/RTO 数字是**目标**，没有实现和演练证据前不代表达到。
5. 比较至少两种候选方案，分别写适合点和风险；不要把校验器输出当选型建议。

若 JSON 无效，校验器会列出错误并以非零码退出；修正临时副本后重试。想验证错误路径时，只在该临时副本里故意把 `write_percent` 改到使两项合计不为 100，运行一次校验，再恢复正确值。不要编辑或删除其他文件来制造测试。

**预期结果：**环境自检以可读/JSON 形式报告当前机器和候选基线差异；自动化测试全部 `OK`；有效需求卡通过 schema 检查，非法读写比例被拒绝。它不对任何产品、卡片的可行性或硬件性能作结论。

## 6. 如何审阅需求卡

一张卡的价值在于暴露未知，而不是字段填得满。评审时可以按以下次序逐项问：

1. **是谁的需求、哪种请求？**是否明确服务边界、读/写比例口径、典型/峰值请求大小和客户端位置？
2. **阈值在哪里测？**客户端端到端还是服务端内部？超时、失败、重试和限流算不算？统计窗口与样本量是否足够？
3. **数据在何时算“写成功”？**同一进程、其他客户端、主机掉电、单盘/整机/站点故障分别有什么承诺？资料来自产品文档、配置、实测还是仅是期望？
4. **范围是否可实现且冲突已显露？**极低 p99、高吞吐、低成本、跨地域强一致和极短 RTO 可能存在资源/延迟冲突。不要把各项独立承诺拼成未经验证的保证。
5. **故障假设是否独立？**副本是否共享机架、电源、账号、控制平面或软件缺陷？备份凭据和恢复环境是否独立？
6. **谁操作和付出代价？**运维人数、备份/恢复、扩容、迁移、安全审计和容量增长成本都属于方案，不只是设备采购价。
7. **什么尚未知道？**把业务量、产品语义、压测设置、故障域、保留策略和成本中的未知显式列出，并为每项指定证据来源或验证实验。

本地需求卡不自动转换为完整架构设计。下一步应把需求映射到可比较候选方案，列出必须通过的正确性/故障测试，再在受控环境测量。性能实验在 M01/M12 学习；持久性和恢复实验在 M07/M15 学习。

## 7. 常见误区与故障排查

- **“p99 < 10 ms 就是快。”** 未说明端到端测量点、请求种类、负载、窗口和失败处理，目标不可复现。
- **“99.99% 可用性代表数据不会丢。”** 可用性和数据耐久性不同；错误数据也可能是可用响应。
- **“复制三份就有三份备份。”** 副本可能同步错误、共享故障域或共享凭据。备份要能保留历史并独立恢复。
- **“RPO 0、RTO 0 是默认需求。”** 这是强目标，不是没有成本的标签；必须说明故障范围、同步确认点、测量方法和系统可接受的不可用状态。
- **“测试工具给出 VALID，需求已通过。”** 校验器只检查 JSON schema 和少数跨字段约束，不检查数字是否合理、术语是否定义、方案是否实现或服务是否达标。
- **比例测试失败：**read/write 应为整数百分比并合计 100；该比例以请求数计，而不是字节数。
- **找不到 `python3`：**实验只要求 Python 3 标准库；不要为自检盲目执行网络安装脚本。可改用已有 Python 3 环境并记录版本，或请课程维护者准备本地解释器。
- **候选 baseline 显示不同：**这是记录而非故障。本课不要求 Ubuntu 24.04.5；后续涉及 ABI 或包版本的实验才检查具体条件。
- **命令改动源样例或临时清理异常：**先确认当前目录是实验目录、临时路径确由本次 `mktemp` 返回；不要用通配符清理更大目录。重新创建一个临时工作目录再开始。

## 8. 练习题

1. 一个服务 90% 是 4 KiB 读、10% 是 8 MiB 写（按操作数计）。为什么“90% 读”不意味着大多数字节流量是读？如果比例按字节统计，需求卡应如何改？
2. 某客户端报 p99 5 ms，但超时请求被排除，另有 1% 超时。这个结果能证明什么、不能证明什么？应如何定义一个更有用的 SLI？
3. 写成功后，进程立即崩溃、单盘失效、整机失效、机房断联分别可能需要不同的恢复点。为每种故障定义可观测的 RPO/RTO 验收方法。
4. 两个副本位于同一主机，但不同 SSD。列出该设计覆盖和不能覆盖的故障，并解释为什么快照/备份另有作用。
5. 把 `requirement-card.example.json` 的工作负载改为均匀随机、写多、工作集大于内存的场景。列出哪些测量方法和存储候选要重新评估；不用实际访问设备。
6. 对服务卡中的两个候选选项写出一个可区分结果的实验：设置、输入数据、成功/失败观察、清理和停止条件是什么？说明为何实验仍不能证明站点级可用性。
