# M00-L01：存储全景与端到端数据路径

> 状态：课程正文　｜　建议课时：100–115 分钟　｜　先修：会使用 Linux 命令行，理解应用通过 API 请求服务即可。无需 NVMe、专用服务器、root 或云账号。课程候选版本与实验边界见[版本与实验环境](../../课程大纲/版本与实验环境.md)。

## 学习目标

完成本课后，你应能：

1. 把介质、设备协议/传输、操作系统接口、存储服务和应用数据模型放在不同层次讨论；不把接口名、设备外形或产品名当成同一概念。
2. 从一个应用读/写请求画出本地文件、块设备、远程块、网络文件系统、对象服务和数据库的端到端路径，并标出缓存、元数据、网络和故障边界。
3. 解释系统调用返回、服务确认、设备完成和持久化承诺之间的区别，提出需要查明的同步、复制和恢复语义。
4. 识别存储系统中常见的简化说法，并用版本、配置、负载和证据限定结论。
5. 为具体工作负载挑出需要进一步测量/确认的存储属性，而不是仅凭“NVMe 更快”或“对象存储可扩展”作选型。

## 1. 从业务动作到存储承诺

“把图片保存下来”是一个业务目标，不是足以实现或验收的存储规格。实现者仍要回答：调用者提供的是字节流还是对象名？谁负责鉴权和元数据？写操作覆盖旧版本还是创建新版本？写成功后同一客户端、其他客户端、掉电恢复分别能否读到？数据需要保留多久？一台机器、一个机房或整个服务不可用时怎样恢复？文件系统、对象 API 和数据库都能保存“图片”，但给调用者的语义、故障处理和运维责任不同。

可以用五个互相正交的问题先定位系统：

| 问题 | 常见取值 | 不应推出的结论 |
|---|---|---|
| 数据由什么介质承载？ | HDD、NAND SSD、持久化介质、内存缓存等 | 介质快不等于应用端到端请求快；固件、队列和软件栈仍有成本 |
| 数据通过什么链路/协议到达？ | PCIe/NVMe、SATA、SAS/SCSI、Ethernet、NVMe-oF、NFS/SMB、HTTP | 接口或连接器不必然唯一决定上层协议和语义 |
| 应用使用什么抽象？ | 字节文件、块地址、对象 API、KV/SQL | 抽象名称不表示底层一定是本地盘、网络盘或某个产品 |
| 请求落在哪个故障域？ | 进程、主机、机架、机房、供应商区域 | “远端”不自动等于高可用；同机多副本不等于独立故障域 |
| 成功响应承诺什么？ | 已接收、已可见、已复制、已同步到特定持久化边界 | `write()` 或 HTTP 200 的字面成功不自动证明掉电后可恢复 |

把本地/远程、协议、抽象分开后，技术图不会误导选型。例如 NVMe 是存储命令集/协议；PCIe 是常见本地传输路径；M.2 是一种外形/连接器规格，可承载 SATA 或 PCIe/NVMe 设备，不能与 NVMe 画等号。RDMA 是网络访问/传输能力，不是存储数据模型；它可减少数据搬运和 CPU 参与，但不意味着整个请求完全不使用 CPU，也不提供文件/对象语义。NVMe-oF 把 NVMe 命令映射到 Fabrics 传输（如 TCP 或 RDMA），它不是“远端设备就和本地设备延迟相同”的保证。

## 2. 按抽象层理解存储类型

### 块设备：可寻址的逻辑块

块设备向上呈现一个有容量的逻辑地址空间。文件系统、数据库或卷管理器可在其上建立自己的布局。块层接口不替应用解释“这 4 KiB 是照片还是索引”；上层须自行维护格式、边界、并发和恢复协议。Linux 上普通文件的读写与直接操作块设备节点也不是同一调用路径。LBA、块大小和安全的文件映像实验在 [M01-L01](../M01-设备与块存储/M01-L01-块设备与LBA.md) 详述。

### 文件：命名空间与文件操作

文件系统以路径、目录、权限、文件偏移等抽象数据。VFS 让不同文件系统实现共同的操作接口；这并不说明所有文件系统拥有相同的持久性、缓存、锁定或崩溃语义。ext4、XFS 等是具体文件系统实现；是否为发行版默认、挂载参数和设备组合都需要按目标系统核对。NFS/SMB 可把文件操作跨网络提供，客户端 VFS 之上增加网络客户端，服务器侧还会有服务进程/内核、服务器文件系统和后端设备。

### 对象：键名、元数据和对象操作

对象服务通常通过 API 对 bucket/key 和对象内容执行操作，并由服务端管理元数据、放置、校验、复制或纠删码等工作。调用者不应假设对象内部布局、实现语言或后端硬件。不同产品即使提供相似的 S3 API，也未必有相同的一致性、版本、错误码、权限或生命周期语义；必须区分 AWS S3 的产品承诺和某个兼容实现的实测边界。

### 数据库及 KV 引擎：更高层的数据语义

关系数据库向调用者暴露 SQL、事务、索引和隔离级别；KV 引擎提供键值操作。它们通常在文件、块或云服务上再实现 WAL、索引、缓存、压实、复制及恢复。RocksDB 是嵌入式 LSM KV 引擎，不等于独立的通用关系数据库；TiDB 是分布式 SQL 系统，其 TiKV 等组件的实现不应与“数据库”一词混作同一层。产品只确认请求时，究竟是本机日志、远端副本还是仲裁达到要求，要看具体产品版本/配置的文档和测试。

这些分类不是互斥的：数据库可以存放在本地文件上，也可以把块设备作为底层；文件系统能由块设备构建，也能由远程服务提供；对象存储可以服务数据库备份，但不因此成为事务数据库。

## 3. 本地文件读写的端到端路径

下面是常见 Linux 缓冲式普通文件路径的概念图。具体系统调用、文件系统、内核版本、挂载选项和缓存状态会改变细节。

```text
应用 / 数据库 / 运行时
  │  read/pread 或 write/pwrite；可能先命中应用自身缓存
  ▼
系统调用边界 → VFS / 文件描述符权限与偏移检查
  ▼
具体文件系统：路径/inode/extent/分配和一致性处理
  ├─ 读命中页缓存 → 将数据交回进程（本次不一定有设备请求）
  └─ 未命中 / 脏数据回写 → Linux 块层 bio/request、队列与调度
                                  ▼
                         存储驱动与控制器命令队列
                                  ▼
                   设备逻辑地址/FTL 或 HDD 控制器
                                  ▼
                              介质

完成沿反向传播；中断/轮询、等待者唤醒和后台回写时序依配置变化。
```

**读路径举例。** `pread(fd, buf, n, offset)` 先经过系统调用和 VFS 的文件对象操作，文件系统把文件偏移映射到数据。若数据已在页缓存，数据可直接复制给调用者；未命中时文件系统安排底层读取，任务可能等待 IO 完成后被唤醒。预读、应用缓存、内存映射、直接 IO、异步接口会改变搬运与等待方式。一次缓存命中不是设备读延迟的测量，一次冷缓存读也不自动代表稳态设备性能。

**写路径举例。** `write()`/`pwrite()` 通常先将数据复制/映射到内核缓存并标记脏页，调用返回后回写可能仍在后台；文件系统还要维护数据块分配和元数据。之后内核将请求提交给块层和驱动。`fdatasync()`/`fsync()` 会请求同步相应数据以及 API 规定的元数据，但软件栈和设备必须正确处理缓存刷新、写入顺序等要求，才能达到某种掉电持久边界。新建/改名文件的目录项持久性还可能需要同步父目录。具体保证由文件系统、挂载方式、块设备、控制器缓存和硬件兑现情况共同决定，不能从单个函数名推导。

这里要区分至少四个事件：应用函数返回、内核接受/完成该次请求、设备报告命令完成、系统按约定确认掉电恢复所需的数据已进入持久化边界。远端服务还会增加服务器接收、服务端日志、复制/仲裁确认等阶段。它们可能重合，也可能分离。

## 4. 其他访问路径：哪些层被替换，哪些仍存在？

### 远程块设备

```text
应用 / 文件系统 / 本地块层 / initiator 驱动
       → 网络传输（例如 NVMe-oF/TCP 或 RDMA）
       → 远端 target / 控制器 / 块设备路径
       → 介质
```

客户端看到块地址，不意味着网络消失；链路拥塞、重传、远端队列、target 故障和网络分区都会影响完成时间。由上层文件系统解释的字节仍要经过客户端文件系统路径。实验版本、target、网络和块设备设置决定观察到的路径；本课程 M00 只做概念与需求建模，不要求连接或写入远端设备。

### 网络文件系统

```text
应用文件系统调用 → VFS → NFS/SMB 客户端与协议
  → 网络 → 服务端文件服务/协议处理 → 服务端 VFS/文件系统
  → 块层/设备 → 介质
```

客户端缓存、锁、委派、重连和服务器导出配置都可能影响语义。跨网络文件访问不是“把本地文件系统替换成透明网络”，缓存失效和服务端故障必须纳入故障模型。

### 对象 API

```text
应用 / SDK → HTTP API、鉴权、重试与请求 ID
  → 对象服务前端 → 元数据/路由/校验/放置
  → 一个或多个后端节点、介质与副本/纠删码
```

具体服务可能继续调用块设备、文件系统或自身对象引擎；端到端路径取决于产品。SDK 重试可能在服务端已执行而响应丢失时产生重复请求，因此写入幂等性、版本/条件写和请求标识需要说明。响应成功是否代表副本数、可读可见性或断电持久性，不可由 API 外观推定。

### 数据库请求

```text
客户端 SQL/KV API → 网络协议/认证 → 查询执行/事务
  → 锁/版本/索引/日志 → 单机存储引擎或复制协议
  → 节点本地文件/块 → 设备
```

数据库可能在内存中完成读取，提交也可能要等待 WAL、远端副本或共识多数派。若产品只在本地日志同步后确认，机房损失如何处理仍是另外的问题；若提交等待多数派，也要查副本是否位于真正独立故障域。SQL 事务保证、块设备顺序和硬件持久化属于不同层的承诺。

## 5. 路径图上的四个标记

绘图时至少标注以下内容，不要只画一排产品名：

1. **请求语义与身份边界：**API、对象名/文件名/LBA、客户端认证和权限在哪里检查？重试是否可能重复操作？
2. **缓存与拷贝：**应用、页缓存、服务端缓存、设备缓存分别在哪？读命中时绕过哪些层？缓存何时失效/回写？
3. **持久化与确认点：**哪个动作改变可见性？哪个动作改变掉电恢复承诺？是否等远端副本/仲裁？明确“未定义”也比臆测更好。
4. **故障域与控制面：**客户端、网络、主机、控制器、机架/机房、服务管理面有哪些独立故障？数据面恢复依赖什么控制面服务？

**例：缩略图服务写对象。** 应用把图像内容、对象名和元数据交给 SDK；网络服务鉴权并路由对象；元数据与内容可能走不同的内部组件；后端将内容持久化后响应。要核实同 key 覆盖语义、成功响应定义、校验、可见性、版本控制和恢复承诺。若没有产品文档/实验佐证，应在图上以“待确认”标注，不把典型实现当作所有服务的事实。

## 6. 常见概念误区与适用边界

| 简化说法 | 适用边界 |
|---|---|
| “M.2 接口通常运行 NVMe” | M.2 是外形/连接器规格；设备可能使用 SATA，也可能使用 PCIe/NVMe。需要核对设备和主板支持的协议。 |
| “RDMA 绕过 CPU 参与” | RDMA 能减少数据拷贝和部分 CPU 处理，但不代表 CPU 完全不参与，也不自行提供数据语义、持久化或故障恢复。 |
| “SPDK 在用户态运行，所以一定更快” | SPDK 提供用户态驱动和轮询等路径，仍需设备绑定、DMA/IOMMU、CPU 核与 NUMA 规划；性能取决于工作负载、硬件和配置，可能以更高 CPU 占用换取延迟。 |
| “手写文件系统提升了固定百分比” | 没有可复现条件的百分比不能推广。比较时须固定语义、文件系统/挂载、内核、设备、缓存、数据集、并发、重复次数和统计口径。 |
| “同步 POSIX 与异步 `io_uring` 是两条简单对立的路径” | `read/write`、`pread/pwrite` 和 `io_uring` 的接口及完成语义不同；异步不等于必然更快，须按目标内核和负载验证。 |
| “某文件系统总适合某类文件大小” | 发行版、配置和负载都会影响结果。根据目标版本文档与同负载测试选型，不从单一规则推导结论。 |
| “FUSE 会自动提供水印、缓存失效或云同步” | FUSE 提供用户态文件系统框架，不自动实现转换、授权、缓存失效、异步上传、冲突处理或持久化语义。 |
| “不同存储产品可以按名称直接互换” | Samba、专用文件服务、Ceph 的 RADOS/RBD/CephFS/RGW 和对象服务提供不同接口与运维模型；应按客户端接口、语义和版本比较。 |
| “嵌入式 KV 引擎等同于完整数据库” | RocksDB 是可供数据库或服务使用的嵌入式 KV 引擎；产品边界由接口、事务、查询和运维能力共同决定。 |

以上概念用于建立分层模型，不能替代对具体实现、产品承诺或性能的版本化核验。

## 7. 本课检查练习

1. 画出 `pread()` 读取一个普通文件时“缓存命中”和“缓存未命中”两条路径；说明哪种情况下可以断言这次操作访问了设备？
2. 一次数据库写入返回成功。请至少列出三种仍未确定的事实：例如掉电后的可恢复性、其他客户端何时可见、机房级故障的恢复点。对每个未知说明要查的文档/实验。
3. M.2 NVMe SSD、SATA SSD、NVMe-oF 远端命名空间和 HTTP 对象 bucket 分别位于什么层次？其中哪些只是连接/传输信息，哪些是上层接口？
4. 为什么把两个副本放在同一主机的两块盘上，不能证明抵御整机故障？为什么异步备份也不必然达到零 RPO？
5. 对某项“性能提升 25%”的主张补写一个最小可审查测量方案。列出硬件、内核、负载、缓存状态、正确性校验和重复/统计要求。
6. 给“图片服务”画一张文件方案和对象服务方案的数据路径图，标出两个方案各自新增的故障点与需要确认的成功响应。
