# M15-L02：端到端正确性、重启与验收演练

## 本课目标

把“命令返回成功”拆成可重复检查的用户可见行为、磁盘状态、重新打开结果和竞争行为。完成后能够用自动化测试和单独新建的临时数据库演示 KV 与对象 API 共存、覆盖、compaction 后恢复、二进制数据原样读回；解释各类失败码与进程故障断言；明确这些演练未覆盖 OS/设备级断电。

## 验收分层：不要把不同故障混作一种

| 层次 | 项目测试 | 应观察到的结论 | 明确未证明 |
|---|---|---|---|
| API 正确性 | put/get/upsert/delete/list；对象二进制、空对象、覆盖、bucket、prefix | 读回等于期望 bytes；对象 namespace 不污染 KV list | 多请求事务、S3 互操作、并发服务 |
| 错误边界 | 非法 KV/object key、超限、缺失、重复删除、init 已存在路径 | 按契约返回 1/2/3 并且不误报成功 | 任意恶意输入/资源耗尽均被防护 |
| 重开/恢复 | 每条测试命令开启新 CLI；混合 KV+对象后 compact 再读 | SSTable + WAL 加载后的状态正确，数据仍可读取 | 机器重启或掉电后数据一定存在 |
| 完整损坏 | WAL/Table CRC 错、格式错误 | fail closed；不静默跳过完整损坏记录 | 自动修复、备份回滚、数据 salvage |
| 进程故障注入 | 部分 WAL、write 后/sync 前、sync 后/响应前、compaction rename 阶段 SIGKILL | 由新进程检查 WAL 尾部、已确认/可能未确认数据、继续写入 | kernel panic、OS crash、控制器缓存、设备断电 |
| 并发约定 | 持有 LOCK 时另一个 CLI 打开同库 | 第二个请求即时失败，退出码 1 | 排队、读并行、写并行、公平性、跨主机锁 |

退出码语义：0 成功、1 存储/IO/锁/格式错误、2 参数或输入错误、3 key/object 不存在。错误消息可辅助诊断，但自动判定应优先依赖 exit code 和数据 oracle，不依赖平台相关 errno 文本。

## 自动化端到端门禁

从仓库根目录执行：

```sh
make -C 'projects/MiniStore' ci
```

该门禁会在 `ci` 目标中先 `clean`，再编译 `build/ministore`（普通版本）和 `build/ministore_test`（仅测试挂点版本），最后运行 `tests/` 下全部黑盒与 benchmark 测试。测试数据库都在 Python `TemporaryDirectory` 下建立并清理，不会触碰用户目录或真实设备。

## 手工 mixed KV/object 验收（仅新建临时目录）

以下脚本从仓库根目录执行。它的清理变量只保存刚创建的 `mktemp` 路径；若中途失败，确认路径确属本次生成后再处理。不要把 `DB` 改成现存目录。

```sh
set -eu
PROJECT='projects/MiniStore'
make -C "$PROJECT" all
BIN="$PROJECT/build/ministore"
TMP_ROOT=$(mktemp -d "${TMPDIR:-/tmp}/ministore-m15.XXXXXX")
trap 'rm -rf -- "$TMP_ROOT"' EXIT HUP INT TERM
DB="$TMP_ROOT/db"

"$BIN" init --dir "$DB"
"$BIN" put --dir "$DB" manifest draft
"$BIN" put --dir "$DB" manifest accepted
printf 'M15\000binary\377payload' > "$TMP_ROOT/input.bin"
"$BIN" object-put --dir "$DB" artifacts sample.bin < "$TMP_ROOT/input.bin"
"$BIN" list --dir "$DB"
"$BIN" object-list --dir "$DB" artifacts
"$BIN" compact --dir "$DB"
"$BIN" get --dir "$DB" manifest
"$BIN" object-get --dir "$DB" artifacts sample.bin > "$TMP_ROOT/output.bin"
cmp "$TMP_ROOT/input.bin" "$TMP_ROOT/output.bin"

set +e
"$BIN" get --dir "$DB" absent >/dev/null 2>&1
STATUS=$?
set -e
test "$STATUS" -eq 3

"$BIN" object-delete --dir "$DB" artifacts sample.bin
```

预期：第二次 manifest 写覆盖 `draft`；`list` 只列 KV manifest；`object-list` 列对象名/size；compact 后新进程能读回 manifest 和原始对象 bytes；`cmp` 成功；缺失 key 返回 3；删除对象成功。命令在独立进程中运行，因而每次重开都会走 TABLE/WAL 恢复入口。手工脚本是演示，不是性能基准。

## 恢复与错误断言如何阅读

- **尾部不完整**：只有 WAL 最后残缺 header/payload/checksum 才截断到最后有效记录并同步。此行为用于容忍写入中途进程退出。
- **完整记录校验失败**：checksum、magic、record 长度或 sequence 错误时拒绝打开；静默跳过可能已确认记录会造成不诚实的数据丢失。
- **sync 错误**：测试注入点在真正 `fdatasync` syscall 前故意返回错误；这是错误传播单测，不代表真实 EIO。重开读取可能看到 write，故调用结果为 uncertain。
- **响应丢失**：同步已成功、进程在打印成功前被 SIGKILL；写入可恢复，但客户端没见成功。上层应 query/compare 目标，不假定 exactly-once。
- **compaction**：测试分别暂停在 TABLE 和 WAL rename 附近；完整数据结果及后续追加写是 oracle。它只覆盖本进程/本次系统启动的目录状态。
- **锁冲突**：测试由另一个 file descriptor 持有 flock，再启动 MiniStore 子进程；验证“失败快”契约，不验证两个请求并行完成。

## 结果解释、反模式和讨论

1. “返回 1 就肯定没写入”是错的：write 已 append 而 sync/error/response 可能不确定。写操作失败后读取当前值并遵从调用方幂等/业务协议。
2. “重开 CLI 等于系统重启”是错的：只验证新进程重读当前 OS/文件系统可见文件。
3. “校验失败后自动删坏文件”并非安全恢复；课程要求完整损坏 fail closed，并让操作者保留数据副本/诊断。
4. 测试通过意味着测试覆盖的断言成立，不表示所有并发交错、文件系统或设备组合均正确。MiniStore 当前没有在线多线程/多进程 server API。
5. 确认自动化未要求云 endpoint、AWS key、Ceph 集群、真实 NVMe、CSI 或 root。可选扩展没运行就记录“跳过/未验证”，不能把本地模拟输出改写成生产演练。
