# M15-L03：基准报告、发布清单与限制复盘

## 目标

本课完成一个可复现、数据有校验、统计口径明确的 MiniStore CLI 负载报告；用发布清单区分构建/测试/文档/安全边界；复盘哪些行为是单机教学实现，哪些外部产品栈尚未集成验证。

## 两种不同的 M12 性能证据

1. **MiniStore CLI 端到端观察（本课新增）**：`projects/MiniStore/bench_ministore.py` 使用 Python 标准库启动真实 `build/ministore` 子进程，跑固定 seed 的 GET/PUT 工作负载；每条 CLI 请求一个新进程，计时包括进程启动、路径检查、打开/锁、从 TABLE/WAL 加载恢复、CLI 解析、put 的 WAL append/`fdatasync`、输出和退出。每个 run 使用新建的临时 DB；setup/final readback 位于测量循环外。它测的是**当前命令行调用路径**，不是常驻服务的内部 IO。
2. **Lab 12 普通文件与缓存模拟**：本地 `pread/pwrite` 普通文件与固定轨迹 cache 模型，不调用 MiniStore。普通文件是 buffered/QD=1；cache 只对比命中率，不测 MiniStore cache。结果不能拿来与本课 CLI 报告作产品性能排名。

两种结果都仅表示当次主机/内核/文件系统/负载条件下的观察。OS 页缓存没有被强制清空；没有真实磁盘延迟隔离，没有硬件掉电测试，也不是云或生产环境结论。

## 运行一个可复现 MiniStore 报告

从仓库根目录执行。该命令只构建项目文件，并在自动创建的私有临时 DB 上运行；JSON 被保存到同一临时根，退出时一并清理：

```sh
set -eu
PROJECT='projects/MiniStore'
make -C "$PROJECT" all
TMP_ROOT=$(mktemp -d "${TMPDIR:-/tmp}/ministore-report.XXXXXX")
trap 'rm -rf -- "$TMP_ROOT"' EXIT HUP INT TERM
python3 "$PROJECT/bench_ministore.py" \
  --operations 60 \
  --keys 8 \
  --value-size 256 \
  --repetitions 3 \
  --write-percent 30 \
  --seed 20261015 > "$TMP_ROOT/ministore-report.json"
python3 -m json.tool "$TMP_ROOT/ministore-report.json" >/dev/null
python3 - "$TMP_ROOT/ministore-report.json" <<'PY'
import json
import sys
with open(sys.argv[1], encoding="utf-8") as stream:
    report = json.load(stream)
assert report["correctness"]["passed"] is True
print(json.dumps({
    "correctness": report["correctness"]["passed"],
    "trace_sha256": report["config"]["trace_sha256"],
    "aggregate": report["aggregate"],
}, indent=2, sort_keys=True))
PY
```

参数边界为 1–1000 操作、1–1024 个 key、64 B–64 KiB value、1–5 次重复、0–100% 写操作；最大合成 payload 32 MiB。报告包含 Python/OS/内核/架构、release binary SHA-256、每轮操作数、读写数、p50/p95/p99/min/max、吞吐、trace hash 和最终数据 hash。所有 GET 都与预期 value 比较，计时结束后再次验证全体 key。`correctness.passed` 为 false/命令退出非零时，不能把性能数字作为有效结果发布。

脚本不接受 DB 或输出文件路径参数，DB 只存在于自动 `TemporaryDirectory`。Shell 的 JSON 输出位置由报告者指定；例子只写临时根。不要将测试路径替换成仓库、用户目录、挂载盘或真实数据库。

可独立运行脚本测试（先构建 release binary，因为含一项小型真实 CLI smoke benchmark）：

```sh
make -C 'projects/MiniStore' clean ci
```

## 如何解读数据

- 单次请求 latency 用最近秩法计算。**每次运行内**有 operation 样本分位数；聚合部分对不同 run 的各自 p50/p95/p99 报告 median/min/max，不把运行级 summary 伪装为所有请求的合并分位数。
- `throughput_ops_per_second` 是全部已计时 CLI 请求除以循环 wall time，非设备 IOPS。测试为单线程、单 outstanding 请求（QD=1）。
- 所有 run 使用同一 seed/轨迹，但独立临时 DB。每条 CLI 都重新 open；每次 PUT 追加并同步 WAL，随后下一条命令要 replay WAL。随着 WAL 增长，读取启动成本也可能增长；这属于现有架构观察，不是稳态 server benchmark。
- 数据 setup 和 final readback 不进入请求样本计时，但 setup 与验证会占用运行时间和系统资源。报告中吞吐只按 workload loop 的 wall time 算。
- 没有清理全局页缓存；重复运行可能命中 OS cache；不要使用 root `drop_caches` 追求“冷盘”。
- 报告性能前记录 CPU/内存、内核、文件系统/挂载、VM/容器环境、compiler、项目 commit、后台负载和电源/温度条件。工具输出没有采集到的硬件信息需要人工补录，不能猜测。
- 提交报告时保留 JSON 的 config/environment/runs/aggregate/correctness/interpretation 字段；若要长期归档报告，把 JSON 复制到课程作业目录而不是临时根，并注明文件是本次机器观察，不提交数据库数据或凭据。

同机基线/变更对照应一次只改一个参数，seed 和其他条件保持不变，每个版本都先运行 `make ci`。不同机器的数字不做排行榜。M12 Lab 12 的安全普通文件方法和限制见 [Lab 12 README](../../labs/lab-12-performance-benchmark/README.md)。

## 发布清单（本地教学版本）

### 构建和测试

- [ ] 在干净工作树运行 `make -C 'projects/MiniStore' ci`；release/test 两个二进制均从源代码重建。
- [ ] 所有自动测试通过，包括 API、对象二进制、错误码、lock conflict、WAL/Table 损坏、重启、compaction 窗口和 M15 混合流程。
- [ ] 完成一次人工新临时目录验收；确认对象 `cmp`、缺失码、compact/reopen 均按契约工作。
- [ ] 可选 benchmark `correctness.passed=true`，报告有 seed、trace hash、binary hash、重复次数、分位数、环境和正确性校验；保存观察值但不写虚构硬件结论。
- [ ] 运行 `make -C 'projects/MiniStore' clean`；确认无测试进程、临时 DB 或无意生成的报告遗留。

### 仓库和文档

- [ ] 确认 `projects/MiniStore/.gitignore` 忽略 `/build/`；不提交二进制、数据库、临时 benchmark 报告、Python cache、密钥或个人数据。
- [ ] README 给出 C++20/G++、GNU Make、Python 标准库先决条件，build/test/clean 可复制命令和明示接口限制。
- [ ] 相对 Markdown 链接指向存在文件；课文完成与候选发行版/云/Kubernetes/SPDK/RGW 集成验证状态分开记录。
- [ ] 变更审查包含 `git diff --check`，提交只含 M15 和最终导航/进度所需变更；不 force push、不 amend。

### 发布说明/用户预期

- [ ] 标记为单机教学原型，独占单进程锁，第二 opener fail-fast；不宣称高可用、分布式一致性或并发 server。
- [ ] 对象 API 明确是本地子集，不宣称 S3/SigV4；不提供认证授权、租户隔离、静态/传输加密和密钥管理。
- [ ] 说明 CRC32 非密码学完整性保护；无生产级备份、恢复、异地副本或供应链/SBOM 证明。
- [ ] 把 SIGKILL、合成同步错误、临时普通文件结果明确标为本机应用路径测试，不宣称 OS crash、真实掉电、控制器 cache 或介质保证。
- [ ] 标注容量/WAL 上限、whole WAL/SSTable startup/load/rewrite、手动 compact、每 CLI 一次 open 和缺少后台任务的运维负担。

## 限制复盘：按证据等级说明

| 主题 | 当前 MiniStore 的实际能力 | 本课程结论边界 |
|---|---|---|
| 本地持久化 | 单机 WAL、CRC、SSTable、manual compact；每个 CLI 新进程重开 | 当前平台黑盒测试验证指定进程路径，不覆盖任意 FS/设备/掉电 |
| 并发 | 一个 `flock` 独占；第二个进程失败 | 不支持多 writer/readers、服务排队、租约或分布式锁 |
| 对象 API | 本地 bucket/key CLI，1 MiB 二进制对象，整对象覆盖 | 不支持 HTTP/S3/SigV4、分页、metadata、multipart、ACL 或 AWS 兼容承诺 |
| 安全 | 私有目录/文件 mode、owner、symlink 检查、合法 key | 不具备 AuthN/AuthZ、租户隔离、加密、密钥、备份、审计与供应链证明；CRC32 不抗恶意篡改 |
| 扩展性 | 256 MiB live-table 上限、64 MiB WAL 上限；map 内存扫描；整表 compact | 不适合大数据/高并发；没有多层 LSM、Bloom、索引 block、并行压实或后台线程 |
| 性能证据 | 本机 CLI subprocess QD=1 的统计摘要 | 不是硬件 IOPS/尾延迟产品承诺；Lab 12 file/cache 工具不是 MiniStore 引擎测试 |
| 集群/平台 | 无网络服务与云/CSI 集成 | Ceph、RGW、S3、Kubernetes/CSI、SPDK、真实 NVMe 需独立版本/环境验证；本地替代不等价于集成证明 |

### 风险与下一步建议

如果把项目从教学提升为生产服务，第一步不是“增加 S3 API”，而是另立需求/威胁模型：稳定的客户端协议与身份授权；multi-process/线程/并发控制；事务/幂等设计；版本升级/格式迁移；写错误与备份演练；文件系统/设备持久性资格验证；加密密钥管理；依赖锁定、SBOM 与签名；容量、监控、恢复目标；经过审查的故障注入与长期测试。所有这些均超出 M15，不应由此处教学实现暗示已解决。
