# M14-L01：存储威胁模型、数据保护与安全变更

> 状态：课程正文　｜　建议课时：110–130 分钟（含 Lab 14）　｜　先修：M00 威胁/故障模型、M05 MiniStore、M07 校验与恢复、M08 对象权限、M13 备份恢复。必做实验只需 Linux 与 Python 3.10+ 标准库，不联网、不需要 root。

## 学习目标

完成本课后，能够：

1. 为一个存储服务列出资产、攻击者、威胁、信任边界和失效影响，并把安全目标与可靠性目标分开描述。
2. 准确区分身份认证（authentication）和授权（authorization），把授权主体、动作、资源、上下文及拒绝默认写成可测试策略。
3. 应用最小权限、租户隔离和安全输入/路径处理，并解释 Unix mode、应用逻辑隔离和独立安全域的差异。
4. 设计静态数据加密、密钥生命周期、完整性校验、依赖供应链审查以及可验证的备份恢复流程。
5. 在执行删除、重建、格式化、密钥轮换等高影响操作前做目标核验、影响评估、审批、回滚和审计。
6. 明确 MiniStore/课程设备实验没有提供哪些生产安全能力，不把教学通过等同于安全认证。

## 1. 先确定保护什么、对谁保护

安全不是一个 `chmod` 或加密选项，而是对**资产、威胁主体、攻击路径、信任假设、影响和控制措施**作出明确判断。存储系统尤其同时承载数据机密性、完整性和可用性：泄露对象、篡改索引/WAL、拒绝写入或让恢复密钥失效，都是安全事件；进程崩溃和设备故障则是可靠性故障，两者可能重叠但不是同一模型。

### 资产清单

| 资产 | 例子 | 主要安全目标/影响 |
|---|---|---|
| 用户数据 | 对象/文件内容、KV value、数据库页、快照 | 保密性、完整性、可用性、保留/删除要求 |
| 元数据 | tenant/bucket/key、ACL、索引、WAL、manifest、校验值 | 元数据泄露可暴露业务关系；篡改会错配或丢失数据 |
| 身份与策略 | 用户/服务身份、角色、租户映射、管理员权限 | 身份冒用或策略绕过可跨租户读取/删除 |
| 密钥和凭据 | 数据加密密钥、KMS 凭据、备份凭据、构建签名密钥 | 密钥泄露可使密文失去保护；密钥丢失可使数据永久不可读 |
| 软件与供应链 | 源码、依赖、构建脚本、编译器、镜像、发布工件 | 恶意/被劫持工件可在授权上下文内读改数据 |
| 可用性与恢复能力 | 容量、队列、冗余、备份、恢复工具和操作人员 | 配额耗尽、勒索/误删或不可恢复会扩大中断与数据损失 |
| 审计证据 | 谁何时读写/删改、权限/密钥变更、恢复和管理操作 | 证据缺失会妨碍发现、调查、问责和合规 |

还要记录数据分类、所有者、位置、保留期限、是否含个人/秘密数据、备份副本和访问主体。最小化采集与保留本身就是减少攻击面；审计日志也可能含敏感 key、租户标识或路径，须脱敏并限制读取。

### 威胁主体和边界

按系统规模选择威胁者，而不是假设一个万能攻击者。示例：未认证远端调用方、拥有独立 OS 账户的本机用户、被攻陷的应用/依赖、试图越权的租户、出错的值班操作、备份/构建平台管理员、介质被盗者。写清对手能否运行同 UID 代码、读宿主机、控制 KMS、修改备份、访问构建系统；这些能力决定哪些控制有意义。课程必做实验只模拟无害本地输入和错误路径，不攻击任何真实服务。

```text
租户/客户端
    │ API 与身份验证边界：TLS、凭据、请求解析、速率/配额
    ▼
存储服务进程 ── 授权策略/租户边界 ── 元数据与数据引擎
    │                                         │
    │ 进程/主机边界：UID、capabilities、      ├─ WAL/索引/快照
    │ seccomp、文件描述符、内核              └─ 文件系统/设备
    │                                              │ 静态数据/介质边界
    ├── KMS/密钥服务边界                         └── 加密密钥在另一权限域
    ├── 备份账户/独立故障域边界
    └── 构建与发布边界：源码 → 依赖 → builder → 签名工件 → 部署

运维人员 ── 变更审批/审计边界 ── 管理 API、删除、恢复、轮换和升级
```

每条边都应问：身份如何建立？数据是否加密？谁能改变策略？错误如何关闭？跨边界的数据/密钥/命令能否被记录？一个 MiniStore 本地 CLI 没有网络入口，但仍有 CLI 参数、文件格式、进程环境、依赖/构建产物和本机目录等边界。

### 一个简化威胁清单

| 威胁 | 资产/影响 | 预防、检测和恢复示例 |
|---|---|---|
| 路径穿越或符号链接替换 | 读写库目录外的文件，或覆盖其他租户/用户文件 | 不把原始 key 拼成路径；严格校验；目录 fd 相对打开、`O_NOFOLLOW`/安全 `openat2` 约束；验证文件类型/属主/权限；专用目录与测试 |
| 越权或租户混淆 | 跨租户读、覆盖、删除或列举 | 从已认证主体映射 tenant；每个对象操作授权；拒绝默认；按租户隔离配额/密钥/备份；负向测试 |
| 密钥或凭据泄露 | 静态数据、备份、线上服务被解密/接管 | 密钥不进源码、日志或普通配置；最小 KMS 权限、隔离存放、轮换/吊销演练、访问审计 |
| 恶意/漏洞依赖或构建器 | 恶意代码以服务权限访问所有数据 | 固定来源/版本/哈希；审查传递依赖、构建脚本和发布来源；SBOM、扫描、签名/来源证明、补丁计划 |
| 误删、错误恢复目标或破坏性变更 | 数据丢失、租户中断、恢复覆盖源数据 | 目标 ID 二次确认、预演、影响清单、恢复到新隔离目标、备份可用性证据、审批和回滚 |
| 勒索/管理员凭据失陷 | 在线副本、快照和备份同时被删/加密 | 独立故障域/账号、离线或不可变副本、分权凭据、恢复演练与告警 |
| 损坏/篡改与审计缺口 | 静默返回错误数据，无法定位责任 | 记录格式边界/校验、端到端读后校验；用 MAC/AEAD 防恶意篡改；安全审计日志和抽样恢复 |
| 资源耗尽/重试风暴 | 服务不可用，其他租户受影响 | 有界输入/请求/队列、租户配额、背压、限速、容量余量、拒绝服务监测与恢复预案 |

风险评估不等于承诺消除所有威胁。明确残余风险、可接受影响、责任人和复核时点；本课表格是小型练习模板，不是组织级合规评估。

## 2. 身份认证不等于授权

- **身份认证（authentication, AuthN）**回答“你是谁/请求主体是谁”，例如证书、短期 token、工作负载身份或本地 OS credential。认证建立一个可验证 principal；传入 JSON 中写着 `tenant=alpha` 不是身份凭证。
- **授权（authorization, AuthZ）**回答“这个 principal 对这个 resource 能否执行这个 action”，例如主体 `svc-A` 是否能 `Get` `tenant-A/object-7`。授权应基于已验证身份、资源归属、动作和必要上下文；缺省拒绝，明确授予最少动作/资源，拒绝也要可审计。

推荐将访问判断表示成策略：`principal × action × resource × context → allow/deny`。检查读取、列举、删除、覆盖、快照恢复、改 ACL、旋转密钥、管理租户等不同动作；“能登录”不自动等于“能管理所有对象”。列举 API 也会泄露元数据，不能只保护 GET。

**常见误区：**把共享 API key 当作用户身份；把隐藏 URL 当授权；只在 UI 隐藏按钮；服务端根据请求体里的 tenant 做隔离；仅认证管理员而不审计管理操作；出错时默认为 allow。应对每个操作的服务端执行路径进行授权，并对失败/超时/未知身份 fail closed。

本课 Lab 把 `principal_tenant` 当作一个**已由调用方提供的教学标签**，只测试拒绝不同 tenant 的请求。没有密码、证书、token 校验或可信身份提供方，故它不是认证实现，也不能证明真实租户隔离。

## 3. 最小权限、租户隔离和输入/路径边界

### 最小权限的范围

将权限缩到执行任务所需的最小主体、资源、动作、时间和环境：应用进程用非 root UID；只给专属数据目录读写；减少 Linux capabilities；可行时限制系统调用/网络出站；管理/备份/部署身份分离；短期凭据和到期撤销；人工值班权限临时提升并审计。容器不是宿主机/内核安全边界的替代品，mount、hostPath、privileged、设备映射和容器 capabilities 会改变风险。

`0700`/`0600` 是本地 Unix mode 的访问限制，不是加密，也不隔离同 UID 的恶意进程、root、已被攻陷的进程或可访问备份的管理员。协作式 `flock` 是并发/误用防护，不是身份验证。文件名随机或路径不可猜也不等于访问控制。

### 租户隔离层次

1. **逻辑授权：**每个对象、目录、列表、覆盖、删除、快照及恢复均在服务端验证已认证的租户主体。不能靠 key 前缀或客户端自报租户。
2. **资源隔离：**分别设置请求/存储配额、并发/带宽、保留策略和审计；限制噪声邻居和资源耗尽的影响。
3. **数据/密钥隔离：**视风险使用 per-tenant encryption key、独立备份策略/密钥、分区/namespace、独立进程/OS 身份或独立集群。权衡隔离强度、运维复杂度、迁移和恢复成本。
4. **验证隔离：**构造 A/B 两个主体，A 的 GET/LIST/DELETE/restore 管理操作均不能触及 B；覆盖 key 猜测、空租户、缓存/索引/错误路径、备份和恢复。只测一次 GET 不充分。

### 解析与文件系统安全

对外部输入定义允许语法、最大长度、编码、数量、数值范围和状态转换；先解析成规范形式，再执行策略，不要在不同层用不同规则规范化。长度/整数溢出、重复字段、坏编码、空值、截断记录、重复请求及错误恢复都要有拒绝/测试路径。对完整但不可信的持久化记录做边界检查；可恢复的尾部短写与完整记录校验失败要区分，遇到无法确认的损坏应 fail closed。

将对象 key 当作**逻辑标识**而非磁盘路径；如必须使用路径，避免字符串拼接后信任，使用已打开目录的相对 fd 操作，拒绝绝对路径、`..`、符号链接/特殊文件并核对类型、属主、硬链接数、权限和大小。仅先 `realpath` 检查然后按路径 reopen 仍可能有 TOCTOU 竞争。Lab 通过目录 fd、`O_NOFOLLOW`、`O_EXCL` 和窄字符白名单示范有限防线；不同平台/文件系统/并发对手下需要进一步审查。

错误响应应让用户能采取行动而不泄露绝对路径、凭据、明文数据、内部拓扑或其他租户是否存在；内部审计记录错误类别、主体、动作、目标标识（按隐私要求脱敏）、结果、时间与关联 ID，保护日志防止篡改/越权读取，并设计保留/删除策略。Lab 只输出固定错误码计数，不保存输入或异常全文。

## 4. 静态数据保护与密钥生命周期

**静态数据保护**要覆盖活跃数据、WAL、SST/索引、临时文件、快照、日志导出和备份。仅加密主数据文件而让 WAL/备份明文，会留下旁路副本。传输加密（TLS）保护网络链路；本地 MiniStore 没有网络端点，但这不代表生产服务不需要传输保护。

### 加密设计

- 使用经过审查的 AEAD（例如 AES-GCM，按 NIST SP 800-38D 的约束使用）或经过维护的密码库，不自创算法/模式。Nonce/IV 不得在同一密钥下重复；记录算法、版本、nonce、tag 和 key identifier，考虑认证附加数据绑定 tenant/key/格式版本，防止记录被调换。
- **Envelope encryption** 可用数据密钥加密数据，再用 KMS/HSM 管理的密钥加密数据密钥；应用只在必要边界短暂取得/使用明文密钥。KMS 权限和审计仍是关键，密文与可解密密钥不要放在同一权限域。
- 密钥要有生成/导入、用途/权限、存放、访问审计、轮换、吊销、备份恢复和销毁计划。轮换不等于立即重写所有数据：定义新写入使用新 key、旧密文如何 rewrap/重加密、key ID 迁移与回滚窗口。密钥丢失会使“备份存在”但数据不可恢复。
- 不把密钥硬编码进仓库、镜像、普通配置、命令行参数或日志；环境变量也可能被进程检查/崩溃转储暴露。限制 secret 读取主体、生命周期和 CI 暴露；使用短期凭据/专门 secret store。
- 加密不能代替访问控制、备份、擦除、应用授权或可用性保护。运行中的服务仍需要解密数据；root/进程被攻陷、内存/日志/临时文件泄露，或密钥与密文一并失陷，仍可能暴露内容。

**完整性术语要分清：**CRC32 用于发现偶发损坏，不抵抗恶意篡改；无密钥 SHA-256 checksum 同样可由攻击者连数据一起重算；HMAC 证明持有共享秘密的一方计算过标签；AEAD 同时提供密文机密性和带密钥的完整性认证（具体保证取决于算法/正确 nonce 管理）。Lab 的 SHA-256 仅是校验教学输入被意外改动，不是 MiniStore/WAL 的恶意篡改保护。

## 5. 依赖和构建供应链

存储进程常有权限读写大量数据，因此一个传递依赖、构建脚本或部署镜像被替换，影响可能超过单个 API 漏洞。依赖安全需要覆盖源代码、包管理器、构建容器、编译器、CI token、制品仓库、发布签名和运行镜像，而不仅是 `pip/npm` 漏洞扫描。

建议建立可执行的发布清单：

1. **库存与锁定：**记录直接/传递依赖、精确版本、来源、license、维护状态和用途；提交 lockfile，校验下载内容 hash。版本锁定提高复现性，不证明该版本没有漏洞。
2. **来源与完整性：**优先可信上游/受控镜像；核对 tag/commit、签名/校验和；生成 SBOM（如 SPDX 或 CycloneDX）；对构建工件生成并验证 provenance/attestation（SLSA 提供构建来源等级框架）。签名只有在签名者身份/密钥和信任根可信时才有用。
3. **检查与处置：**进行漏洞/恶意软件扫描、源码 review、依赖差异审查和许可证审核；记录误报、漏洞影响是否触达实际代码、修补 SLA、升级/回滚计划。扫描器没报问题不等于安全。
4. **构建隔离：**减少 CI 权限/密钥、固定 builder/toolchain、禁用不必要网络和可变下载、审查 install/build scripts；分离提交权限、发布权限与签名密钥；尽可能可复现构建并比对产物。
5. **部署核验：**部署 digest/签名过的不可变工件，保留来源与版本映射；运行时清单与开发 lockfile 对账；发生漏洞时知道哪些数据目录/版本受影响以及如何升级、回滚和恢复。

本课程 Lab 仅运行本地 Python 标准库脚本，没有下载依赖、安装包或调用在线扫描器；它验证的是小范围行为，不是供应链完整性。MiniStore 当前没有本课提供的 SBOM、签名发布、provenance、漏洞响应承诺或可复现构建保证。

## 6. 备份、恢复与可靠性

备份安全和可靠性是一个端到端流程：备份一致性点/范围 → 加密和密钥可用 → 传输与独立保留 → 完整性/恶意删除保护 → 隔离恢复 → 应用校验 → 服务切换。RPO/RTO 依 M13 定义，数值必须有明确测量边界。

- 与生产凭据、主机和故障域分离存放；至少一份副本应能抵御生产管理员/勒索软件凭据误用，按风险采用离线/不可变保留。定期验证保护策略和删除权限，而非只验证写入成功。
- 保存格式/软件版本、manifest、对象数量/范围、checksum/MAC、加密算法和 key ID、密钥恢复步骤、访问策略、时间点与操作记录。验证 checksum 不等于业务一致性；数据库/文件系统需使用其一致性机制。
- 恢复先到**隔离的新目标**，校验目标容量/权限/租户映射、密钥可解密、元数据和对象内容、应用级不变量；检查通过后再审批切换。不要把未经核对的备份直接覆盖生产源。
- 演练全链路：无权限/错误版本/密钥不可用/损坏对象/容量不足等失败路径，测实际恢复时间，记录人的步骤与依赖，并验证来源日志。确保备份账号被撤销或 key 轮换后仍可按设计恢复。
- 快照、复制和 RAID 不自动等于独立备份；同一管理员、集群、密钥或故障域可能同时失效。M07 的 SIGKILL 测试不模拟主机/设备掉电，M13 模型没有真正执行备份/restore，均不能作为生产恢复证明。

## 7. 危险操作审查

危险操作包括格式化/初始化设备、删除目录/卷/对象/租户、`purge`/`zap`、降低副本/仲裁保护、批量权限变更、覆盖恢复、密钥吊销/销毁、升级格式以及执行来自文档/依赖的脚本。运行前按影响级别填写以下检查；高影响操作需独立复核/变更审批：

```text
□ 操作目标：环境/集群/租户/卷/设备的不可歧义 ID；与生产/用户数据隔离？
□ 预览：dry-run、计划删除/修改数量、范围清单和路径展开结果是否审阅？
□ 前提：权限最小化；健康状态/容量/依赖/并发写入检查完成？
□ 数据保护：目标备份点、密钥、恢复测试证据和 RPO/RTO 是否足够新？
□ 影响/批准：blast radius、服务影响、所有者、审批人和执行窗口明确？
□ 恢复：回滚/停止条件、幂等性、部分完成处理和联系人准备好？
□ 审计：执行者、命令/工单、目标、审批、输出摘要和结果安全留痕？
□ 收尾：权限/临时凭据撤销、数据/日志核验、告警恢复和复盘完成？
```

不要将确认提示或通用 dry-run 当作安全保障：目标可能在检查后变化，恢复可能不可能，操作可能部分成功。将检查与执行绑定到不可混淆的目标标识，限制批量范围，重要变更采用双人复核/时间窗口，并预先定义中止条件。本课程必做实验不格式化、删除或写入任何用户指定目录/设备；不需要任何破坏性命令。

## 8. MiniStore 的能力和生产边界

MiniStore README 描述的是**教学原型已经存在的本地路径防误用措施**：`init` 只创建不存在的新目录并置为 `0700`；键有窄字符集；路径目录相对打开、拒绝符号链接；数据目录/内部文件检查 owner、mode、硬链接数及普通文件类型；锁是协作式独占锁；WAL/SST CRC32 检测一部分意外损坏。它不递归清空目标，也不接受设备文件作为数据库。

这些措施不能外推为生产安全。MiniStore 明确**未提供**：

- 身份认证、用户/服务主体和对象级授权；没有多租户安全隔离、角色策略或租户 quota。`bucket`/内部 `@obj:` 只是命名空间，不是 ACL。
- 数据、WAL、SST、备份或传输加密；没有 KMS/HSM、密钥轮换/撤销或安全 secret 管理。当前 CLI 没有远程服务，所以“无 TLS”不代表有安全网络 API。
- 防恶意篡改的 MAC/数字签名：CRC32 只能发现部分意外损坏；攻击者可构造新 checksum。没有安全审计日志或防篡改审计存储。
- 对同 UID 恶意进程/root 的隔离、沙箱、威胁监控、速率限制或抗拒绝服务能力。`flock` 仅用于互斥；不能作为身份/授权系统。
- 自动/在线/异地/不可变备份、灾难恢复工具、密钥恢复或端到端 restore 演练；也没有安全擦除/介质清理保证。
- 本课要求的 SBOM、签名发布、SLSA provenance、漏洞响应 SLA、受支持版本政策或已完成的生产威胁审查。构建/测试通过只是开发检查。
- 主机掉电/设备缓存、硬件加密、真实租户隔离、生产文件系统攻击面和安全认证验证。M07 SIGKILL 仅测进程级故障；本地模式位和临时目录实验不模拟恶意主机/内核。

因此 MiniStore 只适合可信本机上的教学、测试数据和受控临时目录；不得用于敏感/多租户/生产数据或公开网络服务。设备/裸盘实验亦不被视为安全认证。把项目用于任何超出教学的场景前，需要独立威胁建模、架构重审、授权/密码学设计、供应链与渗透测试、备份恢复演练和组织批准；本课程不提供这种批准。

观察报告里的 PASS/拒绝错误码，回答：哪些是系统输入校验，哪些是授权策略，哪些依赖 OS 文件权限？为什么 SHA-256 可发现 accidental corruption、却不能认证写入者？如果 principal 只是用户提供的字符串，越权检查为何不是真实身份认证？提交至少两个替代失败假设和一条生产环境尚缺的证据。

## 检查题与作业

1. 画一个本地对象服务的信任边界图，列出至少 6 项资产、3 种威胁主体和 4 条可验证威胁；给每条威胁标注影响/假设/控制/残余风险。
2. API 收到 `{tenant:"B", key:"x"}`，当前用户经过身份认证为 A。谁决定 tenant？授权检查应该在哪些 GET/LIST/DELETE/恢复路径生效？如何证明 B 的存在性也不会从错误泄露？
3. `chmod 0700`、目录 fd + `O_NOFOLLOW`、加密、HMAC 和 KMS 分别保护什么？它们各自没有解决什么？
4. SHA-256 checksum 和 AEAD tag 的攻击者能力假设有何不同？CRC32 可以作为对象真实性证明吗？
5. 依赖固定到某版本后，供应链还有哪些攻击面？SBOM、漏洞扫描、签名与 provenance 分别提供何种证据、又不能证明什么？
6. 为 2 小时 RTO / 15 分钟 RPO 设计恢复演练：包括独立备份、密钥、隔离恢复、数据校验、计时起止和批准切流证据。列出至少 3 个失败注入点，须使用合成数据。
7. 给一次批量删除/恢复操作写危险操作审查单：如何核对目标、范围、备份新鲜度、审批和中止/回滚？
8. 阅读 MiniStore README，挑出两个当前路径安全机制和五项明确缺少的生产能力。解释为什么这不是“MiniStore 漏洞报告”，而是教学原型的范围边界。
