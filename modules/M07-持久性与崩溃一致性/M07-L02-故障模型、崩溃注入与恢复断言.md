# M07-L02：故障模型、崩溃注入与恢复断言

> 状态：课程正文　｜　建议课时：115–130 分钟（含自动故障实验）　｜　先修：[M07-L01：持久性边界、同步接口与写入顺序](M07-L01-持久性边界、同步接口与写入顺序.md)、[M05-L02：WAL 记录格式与崩溃恢复](../M05-本地KV引擎/M05-L02-WAL记录格式与崩溃恢复.md)。

## 学习目标

学完后你应能：

1. 区分进程崩溃、内核/系统崩溃、设备/电源故障和介质损坏；将结论限制在测试实际覆盖的模型。
2. 为每种注入点写清“已写了什么、是否同步、调用方是否收到确认、重启后应看到什么”。
3. 用 MiniStore 自动测试的子进程 SIGKILL 和测试专用阶段注入，验证不完整 WAL 尾部、同步后响应丢失、sync 错误结果不确定及 compaction 中间状态。
4. 区分可安全截去的结构不完整尾部、必须 fail closed 的完整损坏 record，以及需要业务层处理的未确认写入。
5. 说明这些实验没有验证物理断电、内核崩溃、设备缓存、硬件原子写或真实文件系统损坏。

## 1. 故障模型先于故障注入

“崩溃一致”只有对指定故障集合和存储承诺才有意义。这个项目的自动测试终止的是 **MiniStore 用户态子进程**。OS 内核、页缓存、文件系统和设备仍在工作；这和主机重启/失电后的状态不同。

| 故障模型 | 可能失去/改变什么 | 本课程自动测试？ | 可以得出的结论 |
|---|---|---:|---|
| 进程收到 `SIGKILL` | 本进程栈、堆、未完成用户态逻辑；内核和设备继续运行 | 是 | 子进程不执行清理/响应时，下一进程如何解析当前文件；页缓存中的数据仍可能可见 |
| `write()` 结构性短记录 | WAL 最后一个 header/payload/checksum 不完整 | 是（进程在测试挂点被杀） | MiniStore 只将 EOF 处结构不完整 tail 截回最后有效记录，并同步修复文件 |
| 应用层同步错误 | API 返回错误但底层最终可见性不确定 | 有限：在调用 `fdatasync` 前注入测试错误 | 错误路径不发 `OK`；不能由错误推断操作肯定不存在。没有模拟内核/设备真正返回 EIO |
| OS panic、内核重启、掉电 | 易失页缓存/控制器缓存消失；未完成的目录/数据写可能丢失或重排 | **否** | 不能对这些故障做任何实测持久性结论 |
| 控制器/设备断电、flush 不兑现、原子扇区撕裂 | 易失硬件缓存和介质写入状态未知 | **否** | 不能推断设备级持久性、掉电保护或原子写单位 |
| 介质 bit rot / 任意块损坏 | 已提交文件任意位置可能改变或不可读 | checksum 逻辑有合成字节篡改测试，不是介质故障测试 | 完整 CRC 错误 fail closed；CRC 不会自动恢复数据或定位物理原因 |

直接向真实设备断电、操作裸盘、制造控制器 reset、卸载线上文件系统都不是本实验的扩展步骤。需要硬件掉电认证时，应使用专门的设备实验平台、隔离样机、受控电源和明确的测试方案；本课程不提供也不要求这些操作。

## 2. 测试 oracle：从注入点推导恢复状态

故障实验不能只检查“程序退出了”或“能重新打开”。每个 case 至少要断言：

1. **故障时点：**哪些完整/不完整文件操作已执行？sync 调用是否完成？是否有确认响应？
2. **重启入口：**用新的 MiniStore CLI 进程打开测试库，确保运行恢复逻辑，而不是检查崩溃进程的内存。
3. **状态断言：**`get/list` 的值、缺失 key、WAL 长度或 compaction 之后仍能写入的事实。
4. **故障证据：**明确哪些完整损坏应保留并报错，哪些结构性尾部由程序修复；不把错误数据静默删除。
5. **模型边界：**区分当前启动中可见和电源失效后保证；写明 failpoint 模拟了何种代码阶段，没模拟什么。

MiniStore WAL recovery 的核心规则回顾：记录必须先完整且 CRC/sequence/key 全部有效才应用；只有 EOF 末尾不足固定 header 或不足声明长度时才截断到最后一个有效边界；完整 record checksum/magic/序号不合法时拒绝打开。`fdatasync` 错误不属于“肯定无写入”，恢复后必须重新查询。

## 3. 自动化故障注入实验

### 安全说明

实验使用 `projects/MiniStore/tests/test_ministore.py` 的 `TemporaryDirectory`。测试构建 `build/ministore_test` 时启用 `MINISTORE_ENABLE_TEST_FAILPOINTS`，环境变量 `MINISTORE_TEST_FAILPOINT` 仅对这个二进制生效；正常 `build/ministore` 没有挂点。每个 case 的进程只打开测试自身创建的 `db` 目录，Python 清理该临时根目录。**不要在已有数据库上复用故障脚本或设置该变量运行其他程序。**

### 运行全部（推荐）

```sh
make -C 'projects/MiniStore' clean test
```

Make 同时编译生产二进制和带测试挂点的二进制，然后执行所有 M05 黑盒回归与 M07 故障 case。可单独跑其中一项：

```sh
cd 'projects/MiniStore'
PYTHONDONTWRITEBYTECODE=1 python3 -B -m unittest -v \
  tests.test_ministore.MiniStoreTest.test_sigkill_during_partial_wal_record_repairs_only_the_tail
```

### A. 只写入部分 WAL header 后杀进程

测试先写一个有效 `stable=visible` record，再让测试 binary 只写入下一条 record header 的前 9 bytes，输出到达挂点信号并等待。Harness 对这个子进程发送 `SIGKILL`，然后在新 CLI 进程中 `get stable`。

**恢复断言：**`stable` 仍是旧值；不完整的 `uncommitted` key 不存在；WAL 恢复时截回原来的完整长度并对修复执行 `fdatasync`。这验证的是 WAL EOF 结构性短尾的解析路径，不是任意损坏可修复。

### B. 完整 record 已写，但尚未调用 `fdatasync`

测试在 `write_all(WAL, record)` 完成后、`fdatasync(WAL)` 前停住并被 `SIGKILL`；没有 `OK` 响应。随后本机同一内核打开新进程，测试观察到完整 record 仍在页缓存/当前文件视图中，恢复将其重放。

**正确解释：**未同步、未确认的操作可以在进程崩溃后出现。这个结果说明应用无法把“客户端没收到成功”解释成“操作绝不存在”。它不证明不调用 `fdatasync` 也有持久性；主机断电时这条记录可能丢失。

### C. `fdatasync` 成功，但 `OK` 尚未输出

测试在真正 `fdatasync(WAL)` 返回成功后、应用 map 更新和 CLI 输出之前暂停，再杀进程。新进程重开后 `get synced` 必须得到 `durable`。

**恢复断言：**操作已经越过程序定义的同步提交点，但调用方没有响应。生产 API 需要通过幂等请求或 request ID 解决重试/去重；MiniStore 本身不提供 exactly-once。

### D. 注入同步错误

`inject_wal_fdatasync_error` 只在 test binary 的 `sync_data("commit WAL record")` 路径生效：完整 record 已由 `write_all` 交给文件系统，测试钩子在调用真正 `fdatasync` **之前**返回合成 EIO。命令应返回错误且不打印 `OK`；同一次主机启动中，下一进程能看到页缓存里的完整 record 并恢复它。

**正确解释：**这是对 MiniStore 错误传播与不确定结果处理的逻辑测试，不是模拟内核、文件系统、驱动或设备真正返回 EIO。自动测试所见“记录可恢复”是当前运行环境下的确定观察，不是所有同步错误都必须保留数据的契约。

### E. Compaction 发布阶段被杀

两种挂点都在真实的 `renameat` 已返回后、对应父目录 `fsync` 前：

1. `after_table_rename_before_dir_fsync`：当前命名空间中已有新 `TABLE.sst`，旧 WAL 仍在。重开后 table high-water sequence 跳过已被快照覆盖的旧 WAL 记录；验证值和删除墓碑结果，并继续写入。
2. `after_wal_rename_before_dir_fsync`：表已经先前同步；当前命名空间中 WAL 已换成空日志。重开后验证 snapshot 内容和新写入。

这里的 SIGKILL 不会回滚内核已经执行的 rename，也不会清空内核缓存。因此测试可验证同一系统启动中 MiniStore 对“新表 + 旧 WAL / 新表 + 新 WAL”的恢复逻辑，但**不能**断言掉电后目录项会呈现何种状态。目录 `fsync` 的顺序及新表先同步仍是应用协议的一部分。

### F. 完整记录损坏必须 fail closed

既有自动测试会在完整 WAL record 或 SSTable payload 上翻转一个 checksum 字节，重开必须以错误退出；不会静默截断成旧值。另一测试将完整旧 WAL 与已发布 snapshot 一起恢复，验证 sequence watermark 不回滚快照。这些测试对字节篡改/协议逻辑建模，不等价于真实 NAND/磁盘错误分布或 ECC 行为。

## 4. MiniStore 故障窗口与恢复矩阵

| 注入/事件 | 客户端看到 | 下一次恢复的断言 | 处置边界 |
|---|---|---|---|
| record header/payload 只写了一部分，EOF 在此 | 无 `OK` | 仅截断到最后完整 record；前序状态保留 | 只适用于结构上不完整的末尾 |
| 完整 record 写完，sync 前进程死 | 无 `OK` | 在此进程崩溃实验中完整 record 可见并重放 | 真实断电后可能丢失，结果不确定 |
| sync 返回成功，响应前进程死 | 调用者没有响应 | 重放 record；`get` 可见 | 应用调用者必须处理已提交/未确认窗口 |
| sync 报错 | 命令报错，无 `OK` | 重开查询；记录可能存在或不存在 | 不盲目假定失败等于未执行；用幂等/去重策略处理 |
| 完整 record CRC / 中段 magic / sequence 错 | 命令打开失败 | fail closed，保留损坏证据 | 不自动丢弃完整记录或后续日志 |
| table rename 后、旧 WAL 换名前进程死 | compaction 无成功响应 | 新表 watermark 跳过旧 WAL 已覆盖内容 | SIGKILL 测试只检查当前运行中的 namespace |
| WAL rename 后、目录同步前进程死 | compaction 无成功响应 | 进程崩溃测试重开读取新表/当前 WAL | 不能据此声称电源失效时的目录项保证 |

MiniStore 每次 CLI 只执行一条请求。生产级常驻服务若在追加中途遇到错误，不能仅捕获异常就继续写；需要隔离/标记 WAL、协调恢复、保证事务边界并定义客户端重试语义。MiniStore 不实现这些更大范围的服务职责。

## 5. 恢复说明：课程库 vs 真实数据

对课程新建临时库，可以直接运行测试并让它在测试结束时清理目录。若是在自己运行 MiniStore 时遇到恢复报错：

1. 停止继续写入，不要反复重试产生更多状态；记录错误消息和退出码。
2. 确认目标是自己创建的 MiniStore 数据目录。对真实数据先按组织的数据保护流程制作只读副本/快照；不要在原件上手工 truncate、翻转 checksum、删除 WAL 或临时表。
3. `get/list` 会在打开时运行 WAL/SSTable 校验。尾部结构不完整时，MiniStore 会截回最后有效边界并 `fdatasync`；完整 CRC/magic/sequence 错误会 fail closed，不自动回退或修复。
4. 对 sync 错误或响应丢失的写，使用应用语义重新查询 key/sequence；MiniStore 没有 request ID，不能单靠 CLI 证明某个上层操作只执行一次。
5. 若文件格式 fail closed，保留原件和错误信息，从经过验证的备份/副本恢复；CRC32 不是恢复码。MiniStore 也没有在线备份、WAL salvage、复制或自动灾备机制。
6. 只在全新临时库中重新运行 M07 测试；不得把测试挂点和故障注入命令指向用户现存目录、挂载盘或设备。

## 常见误区

- **“`kill -9` 等于断电。”** 它杀进程但不杀 Linux 内核/页缓存，也不切断设备供电。
- **“未收到 `OK` 就肯定没写。”** 未同步完整 record 也可能在重启后可见；同步成功后响应丢失更会造成已提交但未确认。
- **“EOF 之前任意 checksum 错误都能当作尾部撕裂丢掉。”** 完整坏 record 可能是已确认写或介质损坏，MiniStore 选择 fail closed。
- **“重开一次成功就证明可靠。”** 只说明该环境当前运行状态下解析通过；没有覆盖 OS cache 丢失、控制器缓存和设备掉电。
- **“注入了 EIO 就模拟了硬盘 EIO。”** 本实验在 `fdatasync` syscall 前合成错误，只检验程序错误分支。
- **“故障测试通过就是生产级一致性认证。”** 这里的模型是 MiniStore 的单机协议 + Linux 进程级退出 + 当前本地文件系统；内核、文件系统、设备和硬件保证需各自验证。

## 检查题与作业

1. 比较 B/C 两个注入点：二者都没有 `OK`，为什么不能对恢复结果做同一预测？
2. 注入一条只部分写入 WAL 的尾记录后，为什么可以截断；注入完整 record 的错误 CRC 后，为什么停止打开更安全？
3. 如果一条 put 因 `fdatasync` 返回错误而报错，但下次 get 查到新值，调用者该如何处理重试？MiniStore 缺少什么 API 能力？
4. Compaction 在 table rename 后杀进程时，旧 WAL 为什么不会回滚新 snapshot？这个结论依赖哪个字段？
5. 设计一个“内核重启后数据仍存在”的验证，需要固定和记录哪些软件、文件系统、设备与供电条件？为什么当前课程测试不能替代？
6. 为任意一个 failpoint 写测试卡：故障时序、预期客户端可见性、恢复 oracle、测试通过/失败的判据、不能泛化的结论。
