# M07-L01：持久性边界、同步接口与写入顺序

## 学习目标

学完后你应能：

1. 区分 `write()` 返回、`fdatasync()` / `fsync()` 成功、数据库应用确认和调用方收到响应这几个时间点。
2. 解释内核页缓存、文件数据/元数据、目录命名空间、设备易失缓存分别处于哪个持久性边界。
3. 选择文件 `fdatasync`、文件 `fsync` 和父目录 `fsync` 的对象，并说明它们不互相替代。
4. 画出 MiniStore 的 WAL append 与两阶段 compaction 写入顺序，解释每一个顺序依赖。
5. 说明同步接口依赖文件系统、块层、控制器和介质兑现承诺；本课程不认证真实掉电行为。

## 场景：一次写请求何时可以说“成功”

应用写入一条 KV record，至少涉及几个不同的事件：应用把 bytes 交给内核、内核/文件系统把它们写入某个缓存或队列、同步调用要求栈下达到某个持久化边界、存储引擎更新内存索引并产生响应。把这些事件统称为“写成功”会隐藏关键的崩溃窗口。

```text
应用 buffer
   │ write(2)                         系统调用完成，不等于稳定介质
   ▼
Linux VFS / 页缓存 / 文件系统日志
   │ writeback + block requests
   ▼
块层 / 控制器易失缓存 / 设备介质
   ▲
   │ fdatasync/fsync 要求同步；下层需正确执行 flush/FUA 等约定
   └──────────────────────────────────────────────────────────────
```

在 MiniStore 普通 WAL 文件路径中，`write_all()` 调用 `write(2)` 写 `O_APPEND` 文件。完整 `write_all()` 只保证本程序循环没有遗漏短写；数据通常进入内核页缓存，不能仅凭系统调用返回断言掉电后还存在。

## 1. 同步的对象与接口

| 操作 | 同步请求针对什么 | 典型用途 | 不能推断什么 |
|---|---|---|---|
| `write(fd, ...)` | 把 bytes 交给文件系统路径；可能只写入部分数据 | 追加 WAL、写临时文件 | 不保证数据已经落到非易失介质；短写和 `EINTR` 需处理 |
| `fdatasync(fd)` | 请求同步文件数据及之后读取这些数据所必需的元数据（例如文件长度） | WAL 追加后建立提交边界；MiniStore 的数据文件同步 | 不同步其父目录中的文件名；不认证设备/固件真的兑现持久化承诺 |
| `fsync(fd)` | 请求同步文件数据及文件元数据 | 创建/更新文件内容及相关元数据 | 通常仍需对目录 fd 单独 `fsync` 才建立目录项更新的持久化边界 |
| `fsync(dir_fd)` | 请求同步目录的命名空间变更 | `rename`/创建后持久化文件名更新 | 不代替对新文件内容的同步；不是跨多个文件的事务 |
| `close(fd)` | 关闭文件描述符 | 资源生命周期结束 | 不是 `fsync` / `fdatasync` 的替代品；成功 close 不是提交协议 |

`fdatasync` 与 `fsync` 的精确行为按目标 OS 文档和文件系统检查。Linux 上 `fdatasync(2)` 会同步读取文件数据所必需的元数据；例如 WAL 增长所需的文件长度必须可恢复。若系统要求其他元数据也同步，可使用 `fsync`。对于新文件名、rename、unlink 等目录项变化，通常还需要同步包含该项的目录 fd。

目录同步解决的是**命名空间**边界，不是文件 payload。比如临时表内容已 `fdatasync`，但 `rename(temp, TABLE.sst)` 后进程崩溃：运行时其他进程看到的名字切换具有原子性语义，但在 OS/电源故障后该目录项更新是否持久还取决于目录同步及下层实现。MiniStore 在 rename 后 `fsync` 数据库目录。

## 2. 内存、文件系统与设备缓存层

即使文件系统接受同步请求，端到端持久性还依赖下面的栈正确执行请求：

1. **用户态 buffer：**数据尚未写入，进程退出即丢失。
2. **内核页缓存：**普通 `write()` 完成后数据可能只在 RAM；进程 `SIGKILL` 不会清空内核页缓存，OS 仍可继续 writeback。
3. **文件系统：**数据区和元数据更新可能分批落盘；journal 能保护文件系统自身结构，不自动给应用定义的 WAL 记录提供跨文件一致性协议。
4. **块层/控制器缓存：**请求可能进入易失写缓存。同步路径可能要求下发 flush/FUA 一类命令，但设备/驱动/固件必须正确支持和兑现。
5. **非易失介质与供电保护：**有掉电保护的缓存和设备可有更强的行为；本课程不检查设备规格、固件缺陷、线缆/电源、虚拟化宿主或云盘服务实现。

因此，“我调用了 `fdatasync`”是程序向系统栈提出的同步请求；“同步成功”是在调用约定和正确实现的系统栈下获得的确认，不是模型之外的绝对物理定律。生产系统要基于目标 OS、文件系统、挂载选项、内核/驱动、控制器/设备和虚拟化/远端存储契约做验证。MiniStore 是教学原型，不提供掉电认证。

## 3. MiniStore 的 WAL append 与确认边界

`Store::append_operation()` 的实际顺序：

```text
校验 key/value → 分配 seq → 编码带长度/CRC 的完整 record
   → write_all(WAL, record) → fdatasync(WAL)
   → apply 到本进程内存 map → CLI 输出 OK seq=N
```

`fdatasync(WAL)` 是这条单记录写操作的应用提交点：程序只在它返回成功后更新 map 并打印成功。每个 CLI 进程只执行一条命令，退出后下一条命令重新打开文件并恢复，因此测试自然穿过重新打开路径。

但同步接口失败时，结果可能不确定：内核/设备可能已经保存部分或全部数据，即使调用返回错误。当前调用不更新 map、不输出 `OK`，而是报错退出。用户随后应重开数据库查询实际状态，不应假定失败就等于“肯定没有写入”。同步成功后、程序打印响应前被杀，也会出现写已恢复但客户端没有确认的情况；这不是 exactly-once API。

| 观察点 | 是否确认 | 重启可见性 |
|---|---|---|
| `write` 尚未完整 | 否 | 可能有不完整尾部，MiniStore 会修复合法的尾部截断 |
| 完整 record 已写、`fdatasync` 尚未调用 | 否 | 本机页缓存可能保留 record；不能断言一定有或一定没有 |
| `fdatasync` 返回错误 | 否，结果不确定 | 记录可能完整、部分或缺失；重开查询，项目拒绝猜测 sync 错误必然意味着无数据 |
| `fdatasync` 返回成功，响应前进程被杀 | 引擎已过提交边界，但调用者没收到响应 | 在同步契约被兑现时应重放；调用方需处理结果不确定/幂等 |
| `OK` 已到达调用者 | MiniStore 按其本机文件同步契约确认 | 不等于远端复制、跨机器承诺或本课程的真实掉电证明 |

## 4. Compaction：文件内容顺序与命名空间顺序

MiniStore compaction 把当前 live map 编成带 `max_sequence` 的 snapshot，并且依赖顺序：

```text
TABLE.sst.tmp: write → fdatasync
     → rename(TABLE.sst.tmp, TABLE.sst)
     → fsync(database directory)       # 新表名字先成为同步后的基线
     → WAL.tmp: create → fdatasync
     → rename(WAL.tmp, WAL)
     → fsync(database directory)       # 新 WAL 名称同步
     → 重新打开 WAL 追加
```

- 临时表内容必须在发布前同步；否则 rename 只会发布一个名字指向内容不完整/尚未同步的文件。
- 先发布并同步新表，再替换 WAL。若进程在新表发布后、旧 WAL 轮换前退出，恢复会同时读到新表和旧 WAL；表头 high-water sequence 使恢复跳过快照已包含的记录，不把状态回滚。
- 新空 WAL 文件先同步，再 rename 和同步目录。文件数据同步与目录项同步是不同步骤。
- `rename` 不提供两文件事务。这个协议用表 watermark 和操作顺序处理设计内的窗口；它不能把任意文件系统或硬件故障都变成原子事务。
- 如果 `fsync(dir_fd)` 报错，目录项是否最终持久不能据报错推断为“肯定没发生”；需要停止并检查，不应绕过错误后继续宣称成功。

初始化也要把 `FORMAT`/`WAL`/`LOCK` 文件内容同步，再同步数据库目录和其父目录中创建出来的数据库目录项。对既有 WAL 的追加通常不改父目录中的文件名，因此 append 的提交边界是 WAL `fdatasync`，而不是每次再同步数据库目录。

## 5. 同步错误与工程策略

- 保留操作返回码和错误日志；`EIO` / `ENOSPC` / `EDQUOT` 等不是可忽略的性能提示。
- 对同步失败，要把操作结果作为“不确定”，重开后通过序号/读取确认；上层若有非幂等副作用，需要 request ID 或去重协议（MiniStore 未实现）。
- WAL 写入中途失败后不能盲目继续追加下一条 record。MiniStore 每个 CLI 只做一条操作并退出；长寿命引擎通常要将 WAL/实例置为错误状态并修复/重开，以免在不完整尾部后追加有效记录。
- 对目录 `fsync` 失败，应将文件命名空间状态视为不确定；只看当前路径可见不构成崩溃后持久性证明。
- 文件格式中的 CRC 检测意外损坏，不能决定发生损坏的物理原因，也不提供修复或认证。

## 常见误区

- **“`write()` 返回就已经写盘。”** 返回可能只代表页缓存接受了数据；代码仍需完整写循环和明确 sync 点。
- **“`fdatasync` 与 `fsync` 等价，甚至替代目录 `fsync`。”** 两者针对文件；rename 后的目录项需要关注目录 fd。
- **“rename 是掉电原子提交。”** rename 提供命名空间切换语义，不自动持久化目录变更，更不是多文件事务。
- **“文件系统 journal 保证 KV 事务。”** 文件系统自身一致性和 MiniStore 的 WAL/SSTable 状态机是不同层的协议。
- **“设备发了 flush，所以任何硬件故障都安全。”** 设备、固件、控制器、驱动、虚拟化层是否正确兑现，需要具体环境验证。
- **“进程 `SIGKILL` 测试等价于拔电。”** `SIGKILL` 只杀用户进程，内核、页缓存、文件系统和设备仍在运行。

## 检查题

1. `write_all()` 成功后，哪些副本仍可能只在易失内存？`fdatasync` 成功后又依赖哪些组件兑现承诺？
2. 新 SSTable 文件内容已经 `fdatasync`，但 rename 后没有同步父目录，能否断言重启一定看到新文件名？为什么？
3. WAL 的文件大小变化为什么可能属于 `fdatasync` 的必要元数据，而父目录中的文件名又是另一个同步对象？
4. 如果 `fdatasync` 返回错误，为什么“查询恢复结果”和“盲目重试”有不同风险？
5. MiniStore 为什么先发布新表，再轮换 WAL？sequence watermark 在中间故障窗口做什么？
6. 请列出从应用到设备的 3 个持久性承诺点，并指出本课实验没有验证的层次。
