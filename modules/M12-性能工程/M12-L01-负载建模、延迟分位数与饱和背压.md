# M12-L01：负载建模、延迟分位数与饱和背压

> 状态：已完成　适用环境：Linux；必做实验仅需 Python 3.10+ 标准库。课程基线候选见[版本与实验环境](../../课程大纲/版本与实验环境.md)。本文中的性能数字是实验运行的观测，不是机器/设备保证。

## 学习目标

学完后能够：

1. 把一个性能问题写成包含访问模式、数据集、并发、缓存、持久性和 SLO 的工作负载描述。
2. 区分吞吐、平均延迟、p50/p95/p99 与运行间方差，并说明分位数不等同最大值或 SLA。
3. 设计功能正确性门槛、预热和重复实验，报告每轮结果而不挑选最佳值。
4. 从吞吐平台、尾延迟、CPU/IO 队列和排队趋势识别饱和，并说明背压如何限制资源积压。
5. 纠正“单次 `dd` 数字可推广为设备性能规律”的推理。

## 先定义负载与服务目标

“存储快不快”没有唯一指标。开始前写出**操作和负载**：

| 维度 | 需要固定/记录的例子 |
|---|---|
| 操作 | 读/写/覆盖/删除/范围扫描比例；同步点与 durability 语义 |
| 尺寸与局部性 | 块/value 大小、顺序/随机、key 分布、热点/长尾、working set |
| 并发模型 | client/thread 数、未完成请求上限、队列深度、closed-loop 或 open-loop 到达率 |
| 数据/引擎状态 | 新库或已填充库、数据规模、compaction/flush 状态、压缩与校验配置 |
| 缓存 | 应用缓存、引擎 block cache、OS 页缓存、设备缓存；预热及复用方式 |
| 成功条件 | 返回值/数据校验、错误率、是否计入 retry、超时与失败请求如何统计 |

SLO 也要落到用户语义，例如“p99 成功读延迟低于预算、错误率满足上限、持续吞吐达到目标”，并规定测量窗口和请求量。不能把设备顺序大块写的带宽等同于数据库小随机同步写的延迟。

## 吞吐和延迟是互补量

- **IOPS / ops/s**：单位时间完成的操作数。
- **带宽**：单位时间完成的字节数。明确十进制 MB/s (`10^6`) 或二进制 MiB/s (`2^20`)；不要混写。
- **延迟**：一个请求从指定起点到指定完成点经过的时间。要写明是否包含排队、序列化、校验、同步以及客户端开销。
- **分位数**：p50 是中位数；p95/p99 是排序样本中相应比例不超过的经验阈值。p99 不是“最慢值”，也不是对未来 SLA 的证明。报告样本数、错误/超时和分位数算法。

尾部很重要：100 万请求中，1% 的慢请求约有 10,000 个。对延迟敏感用户而言，均值可能掩盖排队、GC/compaction、flush、锁竞争和后台恢复造成的尾部。p99 的估计需要足够样本；只有几十个操作时，p99 几乎只是最大样本附近的读数。

M12 Lab 12 使用最近秩法（nearest rank）计算每轮 p50/p95/p99，报告逐轮与合并样本分位数。合并值只描述所有样本合并后的分布，不能替代“不同运行之间是否稳定”的分析；请同时查看每轮分布。另报告每次运行吞吐和误差范围。正式评估可重复更多轮，采用运行级中位数、最小/最大范围或 bootstrap 置信区间；不要把同一轮内高度相关请求伪装成独立机器样本。

## 正确性是性能测量的前置门槛

建立两条独立验收线：

1. **功能正确性（pass/fail）：**写入/读取结果、数据 checksum、顺序和错误语义符合预期；工作负载完全结束且无遗漏/重复。脚本的校验时间通常不计入 I/O 延迟样本。
2. **性能观测（measurement）：**带单位报告吞吐、延迟分位数、运行间变化、CPU/内存/队列与环境。正确性通过并不使速度数字变成硬件保证；吞吐增加也不能抵消数据错误。

运行前固定参数和随机种子；先验证小数据集；把准备/填充、预热、测量、校验分开；至少多次运行并保留所有结果。每次只改变一项关键因素。若校验失败、错误率上升或测试参数不一致，应判该组结果不可比较，而不是删除慢样本。

## 缓存与预热：冷/热不是一个开关

“缓存”至少可能指应用层缓存、MiniStore/数据库内部缓存、Linux 页缓存和设备自身缓存。重复读同一个小文件可能由内存满足；短时 buffered write 主要测到的可能是页缓存接受速度，而不是介质持久写入。`O_DIRECT` 也不能自动代表真实冷盘或持久写。

报告中准确写“第一次读/重复读”“启动后的初始访问”“运行间复用 OS 页缓存”等观测状态；不要声称“冷缓存”，除非控制并验证了涉及的每层缓存。课程主线**不要求、不建议学生清空系统页缓存**（如全局 `drop_caches`），不为了跑分损害其他用户/进程的工作集。Lab 12 的普通文件数据准备会 `fsync`，但不逐条同步基准写；重跑可能复用页缓存，JSON 明示状态未控制。

## 饱和拐点、队列与背压

提高并发/queue depth 常先增加可重叠工作，之后增加排队而不是完成能力。观察 QD/线程数扫描中的**吞吐与 p95/p99**：吞吐不再明显增长而尾延迟持续上升，通常提示资源已饱和或排队变长。结合 CPU、内存带宽、锁/线程等待、设备利用率/队列、文件系统与后台 flush/compaction，确认瓶颈位置；单看利用率百分比不能定位因果。

对稳定系统，可用 Little 定律作粗略一致性检查：平均在系统中的请求数约为到达率乘平均时间（`L = λW`）。不能把它误用为任何场景下的延迟预测；必须有稳定观察窗，且到达率、完成率、排队定义一致。

**背压**把过载转成受控等待/拒绝，而不是无限增长的内存队列、重试和延迟：限制并发/待处理请求/字节数；达到上限后阻塞生产者、返回可重试错误或降低后台任务速率；定义 timeout、取消、重试抖动与恢复策略。评估时不仅看峰值吞吐，还要记录饱和后 p99、错误率、队列长度及负载回落后的恢复时间。后台 compaction、GC、复制重建都可能与前台争用资源。

## 单次 `dd` 结果的适用边界

单次 `dd` 测量不能作为通用设备性能结论。`dd bs=` 调整用户态缓冲/调用粒度，不等于 NVMe 命令或闪存页大小；块层可能合并或拆分请求，结果还受并发/队列、设备状态、写回、垃圾回收、CPU、预处理和持久化语义影响。测量必须记录完整环境、负载、重复分布和错误边界，不能从一次运行推出“IO 次数是唯一原因”或预测另一台机器的带宽。

任何 `of=/dev/...` 写入都可能覆盖设备数据、分区或文件系统元数据，**不得作为课程基准操作**。课程实验只使用自动创建的普通临时文件和合成模型。安全边界与单位说明见 [M01-L02](../M01-设备与块存储/M01-L02-SSD内部行为与块存储路径.md)。

## 课后检查

1. 为 4 KiB 随机读和 1 MiB 顺序异步写分别写工作负载卡；二者可以直接比较哪一个更快吗？缺了什么条件？
2. 200 次样本报告 p99 有哪些限制？为什么三轮运行内的 60 万个请求也不等于 60 万次独立机器实验？
3. “p50 没变化但 p99 变为 5 倍”可能是什么排队/后台任务现象？还要观察哪些量？
4. 普通 buffered 写返回后即使 checksum 正确，是否验证每笔写已持久化？若任务是 sync write，应改变哪些语义和测量点？
5. 设计一个有界队列方案：队列达到容量时如何处理生产者、超时、取消和重试？怎样报告恢复阶段性能？
6. 一份 `dd` 基准报告中哪些信息缺失时不能推广其结果？为什么不应将裸设备作为未隔离的实验目标？
