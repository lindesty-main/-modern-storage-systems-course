# M11-L01：MVCC、隔离级别与冲突判断

> 建议课时：90–105 分钟（含 Lab 11 前半）｜先修：M05 本地 KV、M07 持久性、M10 Raft 基础｜产品案例版本：TiDB/TiKV v8.5.8（仅作版本化案例；本课不要求安装）

## 学习目标

学完后你应能：

1. 用 `start_ts`、`commit_ts` 和版本链解释 MVCC 快照读及读己之写。
2. 区分快照隔离（SI）、冲突检测和可串行化；知道 SI 仍可能出现写偏序。
3. 对一个事务判断读到哪个版本、何时发生写写冲突或锁冲突，以及哪些异常不能只靠 MVCC 排除。
4. 运行 [Lab 11](../../labs/lab-11-transaction-simulation/README.md) 的本地模型，并说明模型没有覆盖的真实数据库语义。

## 1. 为什么需要并发控制

事务把一组读写当作一个逻辑单元。多个事务并发执行能提高吞吐，但必须定义它们彼此能观察到什么，以及冲突时谁等待、谁失败。**隔离级别是并发执行可观察行为的契约**，不是“是否有锁”的简单开关；不同数据库即使使用相同级别名称，也可能有实现与细节差异。

MVCC（multi-version concurrency control，多版本并发控制）不必让读者和写者为每个读操作互相阻塞：写入产生新版本，读事务按自己的快照时间戳选择可见版本。旧版本还须在不再被活跃快照需要后才能安全回收；课程模拟器不实现版本 GC。

## 2. 用时间戳选择可见版本

抽象版本链：

```text
key = account:A
  (commit_ts=31, value=100)  ← 较新
  (commit_ts=24, value=80)
  (commit_ts=12, value=50)   ← 较旧

事务 T 的 start_ts=25：读到 commit_ts 最大且 <= 25 的版本，即 value=80
```

事务开始时取得 `start_ts`。对 key 的快照读选择 `commit_ts <= start_ts` 的最新已提交版本；事务自己的暂存写入优先（read-your-own-writes）。提交时取得 `commit_ts`，将写集发布为新版本。这里的时间戳是**逻辑排序标识**，不是直接读取各节点墙钟。TiDB 案例中的 TSO（Timestamp Oracle）由 PD 相关机制提供全局有序时间戳；课程模型只用一个单进程递增计数器，不模拟 PD、时钟同步或 timestamp 等待细节。

### 常见隔离级别：概念地图

| 隔离语义（概念级） | 典型保证/限制 | 需要留意 |
|---|---|---|
| Read Uncommitted | 允许读到未提交数据（脏读） | 产品可能不支持或映射到更强语义 |
| Read Committed | 每条语句看到开始时已提交的数据 | 同一事务两次读可能看到不同提交 |
| Repeatable Read | 事务内重复读有稳定性保证 | 幻读、范围锁和具体行为随实现而异；不能仅凭名称断言 |
| Snapshot Isolation (SI) | 事务读同一逻辑快照；通常检测并发写同一数据项 | 不等于可串行化，可能发生 write skew |
| Serializable | 结果等价于某个串行执行顺序 | 可用锁、验证或 SSI 等实现，成本和失败模式不同 |

SQL 标准级别与产品实现之间存在复杂边界。应查目标数据库的版本化隔离说明，不把 MySQL、PostgreSQL、TiDB 的“RR/SI”行为直接互换。

## 3. SI 的写冲突判断与写偏序

本课 Lab 模型采用一种明确、有限的 SI 规则：

- 事务的读固定在 `start_ts` 快照。
- 写入前先为写集 key 加锁（prewrite）；若另一个未决事务已持有锁，则不能继续。
- 若该 key 最新已提交版本的 `commit_ts > start_ts`，当前写事务发生写写冲突，按 **first-committer-wins** 模型拒绝/回滚。
- 只校验写写冲突，不检查所有读集之间的谓词依赖。因此，对不同 key 的并发写入仍可能违反跨行逻辑约束。

**写偏序（write skew）示例：**两位值班医生 A、B 都在岗，规则是至少一人值班。事务 T₁、T₂ 都从同一快照读到 A、B 均在岗；T₁ 将 A 设为离岗，T₂ 将 B 设为离岗。写集分别是 A 与 B，没有相同 key 的写写冲突，SI 允许两者提交，结果却无人值班。

```text
T₁: read(A=on, B=on) ── write(A=off) ── commit
T₂: read(A=on, B=on) ── write(B=off) ── commit
                                  => A=off, B=off（违反业务不变量）
```

修复业务不变量需要更强的协调，例如锁定共同保护记录/谓词、把约束改造成对同一冲突 key 的写、或使用目标产品支持的可串行化事务方案。具体方案必须按该数据库的 API、隔离保证和冲突语义验证。

### 不要混为一谈的几种冲突

- **写写冲突：**同一 key 有更新版本晚于事务快照，或已有未决锁；通常导致等待、冲突错误或重试。
- **锁冲突：**另一个事务已 prewrite/加锁但结果未明；这可能是事务仍在执行，也可能是协调路径故障后的遗留锁。
- **约束冲突：**唯一键、非空、检查约束等，由数据库的索引/约束机制判定，不等同于 SI 的写写验证。
- **写偏序：**读集合相互依赖而写集合不同，普通 SI 写写冲突检测可能发现不了。

事务重试不能盲目重放有外部副作用的业务逻辑；幂等键、去重和调用方重试边界是应用层设计。

## 4. 实验：可见性、冲突和写偏序

运行：

```bash
cd labs/lab-11-transaction-simulation
python3 -m unittest -v test_transaction_sim.py
```

测试会构造固定的版本链和时间戳，检查快照读、读己之写、first-committer-wins、锁冲突时清理部分 prewrite，以及医生值班写偏序。无需数据库、网络、云服务、第三方包、root 或真实数据目录。

实验只实现单版本化 key 的字符串值，使用显式逻辑时钟和简单 SI 冲突规则；不实现 SQL、范围/谓词锁、唯一索引、死锁检测、隔离级别配置、版本回收、并发线程、持久化或真实 TiDB 事务模式。测试通过只说明这些模型规则按预期工作。

## 5. 检查题

1. `start_ts=50` 的事务读一个版本链 `(commit_ts=20, 30, 60)`，读到哪个版本？之后 `commit_ts=60` 的版本能否改变它的快照读？
2. 两个 SI 事务改写同一 key，后提交者为何需要冲突检查？如果写入不同 key，SI 是否自动保证跨 key 约束？
3. 为什么“使用 MVCC”不等于“没有锁”或“可串行化”？
4. 写偏序怎样改造为两个事务都会产生同一冲突点？列出一种业务层方案并指出要核对的产品保证。
