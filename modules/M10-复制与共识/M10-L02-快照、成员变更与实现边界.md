## 1. 日志变长后为什么需要 snapshot

若日志从系统创建开始永久保留，重启恢复和新节点追赶都要读取越来越长的前缀。Raft 允许应用对已经提交并应用的前缀做快照，持久化应用状态，并丢弃该前缀的逐条日志。

一个能接续日志匹配的快照至少要描述：

- 快照覆盖到的 `lastIncludedIndex` 和该索引对应的 `lastIncludedTerm`；它们构成压缩后日志的匹配边界。
- 应用状态的快照内容（或可恢复该状态的数据/元数据）。不能只记录“截断到索引 N”而没有状态。
- 当前 membership 配置状态及任何进行中的 joint configuration 信息，以便恢复后的协议继续使用正确的 voter/quorum 规则。

```text
snapshot state | lastIncludedIndex=120, lastIncludedTerm=8 | retained log 121 ...
       │                          │
       └─应用状态快照             └─后续 AppendEntries 的前缀校验基点
```

Leader 截断已安全保存的前缀后，如果 follower 的 `nextIndex` 落在快照边界之前，普通 `AppendEntries` 已找不到所需旧日志，leader 需要发送 `InstallSnapshot`。Follower 安装快照并建立新边界，然后接收其后的日志条目。若本地压缩边界处的 term 匹配，协议可保留与快照前缀一致的后缀；否则必须按正确性规则丢弃冲突的未提交后缀。已提交状态不能因接收快照而回滚。

快照生成应来自**已提交且已应用**的状态。快照与日志切换、持久化原子性、校验和、损坏恢复是实际实现的关键；只在内存里复制一个 Map 并不证明掉电安全。

**快照不是备份：**它通常和 Raft 日志/状态保存在同一节点或同一故障域，提供日志压缩与恢复加速，不自动提供独立故障域、历史版本、误删恢复、异地灾备或抵御管理员错误的能力。需要另行设计和验证备份/恢复。

## 2. 成员变更：旧多数派到新多数派要有安全交接

多数派依赖当前 voter 集合。若旧配置 `C_old` 与新配置 `C_new` 的多数派彼此不相交，直接在不同节点上各自采用一套成员表，可能出现两个互不知情的组都认为自己拥有 quorum。成员变更本身必须由共识日志排序，并使用重叠的过渡规则。

Joint consensus 的概念状态如下：

```text
稳定 C_old
   │ leader 将 C_old,new 写入自己的日志；之后按 joint quorum 判断
   ▼
联合配置 C_old,new
   ├─选举 quorum：C_old 多数派 AND C_new 多数派
   ├─日志提交 quorum：C_old 多数派 AND C_new 多数派
   └─提交 joint entry 后，leader 追加 C_new entry
          │ C_new entry 用 C_new 多数派提交；各节点见到后采用 C_new
          ▼
稳定 C_new
```

Raft 论文的关键细节：一个节点把新配置条目加入日志后，就使用该最新配置做后续决策，不必等条目已提交才切换；因此 joint entry 的提交需要**旧配置与新配置各自的多数派**。joint entry 提交后，再追加 `C_new` 条目；最终配置按 `C_new` 多数派提交，节点收到该条目时开始使用 `C_new`。过渡期间不同节点可以在不同时间看到新配置，但不存在旧/新两个组都能独立决策的窗口。不要把“旧配置多数派提交 joint、final 再要双多数派”说成 Raft 论文的通用步骤；具体实现可能采用不同配置切换规则，下文会说明 etcd v3.6.0 的版本化差异，不能把这些流程混为一谈。

过渡期间需要新节点先追上必要日志，再使其参与新配置的投票/提交。被移除的节点不应继续计入新 quorum。若分区只允许旧配置形成多数派、无法形成新配置多数派，joint entry 就不能提交；等待可达性恢复，而不能强行把配置翻转为新表。joint 已提交后，若新配置有 quorum，最终 C_new 条目可由新配置推进。

Lab 10 按 Raft 论文的 quorum 阶段模拟上述约束：leader 开始 joint entry 时启用双配置 quorum，joint entry 本身需要双多数派；最终 C_new entry 在模拟器切换到的 C_new quorum 下提交。为使小型状态机可读，cluster 对象集中切换有效配置，省略真实节点逐条观察日志后异步切换配置的过程；该抽象不等价于产品消息时序。

## 3. 论文算法对照 etcd Raft v3.6.0

Raft 论文定义状态机和安全性要求；etcd Raft 是 Go 共识库的一个具体实现。固定源码阅读基线为 [`etcd-io/raft` tag `v3.6.0`](https://github.com/etcd-io/raft/tree/v3.6.0)，peeled commit 为 [`f35a02212416d045c574e30aa59d4b07c4b8d732`](https://github.com/etcd-io/raft/commit/f35a02212416d045c574e30aa59d4b07c4b8d732)：

- [`README.md`](https://github.com/etcd-io/raft/blob/v3.6.0/README.md)：库的集成契约和应用层职责入口。
- [`raft.go`](https://github.com/etcd-io/raft/blob/v3.6.0/raft.go)：Raft 节点状态、消息处理和复制路径，可从 `Step`、term 检查、AppendEntries/投票处理入口阅读。
- [`rawnode.go`](https://github.com/etcd-io/raft/blob/v3.6.0/rawnode.go) 与 [`node.go`](https://github.com/etcd-io/raft/blob/v3.6.0/node.go)：同步式 `RawNode` 与异步 `Node` 外部驱动接口。
- [`confchange/confchange.go`](https://github.com/etcd-io/raft/blob/v3.6.0/confchange/confchange.go) 与 [`raftpb/confchange.go`](https://github.com/etcd-io/raft/blob/v3.6.0/raftpb/confchange.go)：配置变更状态及 joint transition 处理；应以 v3.6.0 的 API/注释为准，不把本课伪代码当成配置变更调用范例。

可用下表连接算法术语与实现观察点：

| Raft 抽象 | etcd Raft 阅读线索 | 应用层责任/边界 |
|---|---|---|
| 节点收到消息或本地 tick | `Step`/`Tick`；`Node` 或 `RawNode` API | 库不替应用创建真实网络，也不替应用选择操作系统定时器和部署拓扑 |
| 持久 term、vote、entries、snapshot | `Ready` 提供需保存的状态/日志/快照；`Storage` 接口和 MemoryStorage 实现 | 调用方提供/管理存储；必须按版本化集成契约持久化并处理同步要求，不能把内存 `Ready` 等同于数据已落盘 |
| 发出的 RPC、待应用条目 | `Ready.Messages`、`CommittedEntries`、`Advance` 生命周期 | 调用方负责传输消息、按序应用已提交条目并推进 Ready；重试、停机和恢复由集成系统处理 |
| membership change | `ConfChange` / `ConfChangeV2`、`confchange.Changer`、joint state/AutoLeave | API 版本、何时应用配置、自动离开 joint 及 voter 变更限制按所读 tag 核实；不是任意修改 voter 列表 |

**实现与论文的差异要按实际 API 追踪。** v3.6.0 的 README “Implementation notes” 明确说明其成员变更规则与 Raft thesis 第 4 章的描述有差异：其配置变更 invariant 是一次改变一个节点，并指出实现将变更在条目应用时生效，因此该配置条目按旧成员关系提交；同一 tag 也提供 `ConfChangeV2` 和 joint configuration helper。阅读时应沿当前调用路径确认使用哪种变更方式，不能把论文伪代码、库 README 与 `ConfChangeV2` 当成无差别的单一流程。Lab 10 则刻意只演练“旧 quorum 提交 joint entry → 双配置 quorum → 最终稳定配置”的教学状态机。

这是“读固定版本源码”作业，不是“实现兼容 etcd”的目标。v3.6.0 在此是课程阅读基线，不宣称该版本是课程当前最新版本，也未在 Lab 10 中构建/调用 Go 库；课程模拟器仅用 Python 标准库。

## 4. 与 Ceph MON Paxos 的比较：相似的是问题类别，不是协议

| 对照点 | Raft（本课） | Ceph MON |
|---|---|---|
| 本课依据 | Ongaro/Ousterhout Raft 算法与 etcd Raft v3.6.0 实现阅读 | Ceph Tentacle 版本化 MON/HA 文档及 M09 说明 |
| 状态/用途 | 通用复制状态机的日志、leader 和配置模型 | Ceph Monitor 协调集群 map/控制状态的 Paxos-based 机制/实现 |
| 名词和证明 | `term`、`RequestVote`、`AppendEntries`、Raft log matching | 不把 Raft RPC、Raft term 或 Raft joint-consensus 细节硬套到 MON |
| 多数派 | 按 Raft 当前成员配置的 quorum 与日志安全规则 | MON quorum 属于 Ceph 自己的控制状态一致性路径；OSD/PG payload 复制是另一层 |

Ceph MON 不是 Raft。Paxos 也不能仅因“没有叫 leader 的组件”或“同样取多数票”而被说成 Raft；要比较协议，必须针对其具体状态机、角色/任期、提交语义和实现版本。相关入口：[Ceph Tentacle 高可用与扩展性文档](https://docs.ceph.com/en/tentacle/architecture/scalability-high-availability/)；课程对照和 Ceph 数据路径见 [M09-L01](../M09-分布式存储与Ceph/M09-L01-故障模型、故障域与Ceph放置基础.md)。

## 5. Lab 10：确定性故障与状态轨迹

进入 [Lab 10 说明](../../labs/lab-10-raft-simulation/README.md)：

```bash
cd labs/lab-10-raft-simulation
python3 -m unittest -v test_raft_sim.py
python3 raft_sim.py --demo
```

在 Python REPL 或临时脚本中按固定事件推进：

```python
from raft_sim import RaftCluster

cluster = RaftCluster(("n1", "n2", "n3"))
cluster.start_election("n1")
cluster.run()                            # 处理投票/选举消息
cluster.partition(("n1",), ("n2", "n3"))
cluster.propose("write-x", leader_id="n1")
cluster.run()                            # 少数派 leader 的 entry 不会 commit
cluster.start_election("n2")
cluster.run()                            # 多数派分区可选出更高 term leader
cluster.assert_safety()
```

测试覆盖多数派选举、无 quorum 选举、日志新旧投票约束、过期 leader 退位、复制与 commit/apply、旧 term 提交规则、冲突未提交后缀替换、leader crash/restart、快照安装追赶、joint quorum 两边约束及成员切换。

### 模型边界（必须在实验报告里写出）

- 消息 FIFO、明确投递，节点和分区只由用户事件触发；没有真实时间、延迟分布、随机 election timeout、并发消息竞态或丢包重传定时器。
- `run()` 把可达消息持续处理到队列为空；这不是网络仿真器，也不模拟真实拓扑带宽/延迟。
- 内存中的 `currentTerm`、日志和快照只在模拟对象中保存；它没有 fsync/WAL/磁盘故障，不能证明断电持久性。
- leader commit 使用索引确认和 quorum，但未实现线性一致读协议、客户端重试去重、领导租约、leader transfer、pre-vote、真实 no-op 行为、流控/批处理或 production membership API。
- 快照应用状态以命令序列表示；membership 配置在 leader 追加 joint/final 配置 entry 时由 cluster 对象集中切换，简化了真实节点按各自日志异步观察配置的流程。joint entry 使用旧、新配置双 quorum，最终 C_new entry 使用新配置 quorum。成员变更要求当前 leader 留在新配置，不模拟移除 leader 的领导权转移。
- 非拜占庭 crash/网络故障模型；不包含恶意节点、磁盘静默损坏、时钟漂移检测和安全性证明执行。

因此模拟器用于观察算法状态转移与写测试，不是 etcd Raft 的替代品、可部署协议、分布式 benchmark 或高可用证明。
