# M13-L01：存储可观测性、健康与恢复目标

> 状态：课程正文　｜　建议课时：100–120 分钟（含 Lab 13）　｜　先修：M00 工作负载/SLO、M07 持久性与恢复、M12 延迟分位数。必做只需 Python 3.10+ 标准库与本机 loopback。

## 学习目标

学完后能够：

1. 从用户可见 SLO 推导指标、结构化日志和 trace，并说明三者的成本、敏感信息与丢失模式。
2. 为存储系统定义健康/readiness 和容量告警，不把“进程还活着”“卷可写”与“数据可恢复”混为一谈。
3. 设定 RPO/RTO，设计有版本、有校验且经过恢复演练的备份流程。
4. 根据本地合成观测证据定位延迟、容量、错误、备份和遥测缺口问题，同时标出未知项。

## 1. 从 SLO 开始，而不是先装仪表盘

“存储正常”要落在用户请求和数据安全语义上。先写清**谁在观察、观察哪条路径、观测窗口与动作**：

| 目标/问题 | 例子 | 需固定的定义 |
|---|---|---|
| 可用性/错误 | 客户端成功率、超时、拒绝、重试 | 统计哪些请求，重试算一次还是多次，HTTP/引擎错误如何分类 |
| 延迟 | GET p95/p99、写入确认延迟 | 起止点、是否包含排队/重试/校验/flush、直方图桶和样本数 |
| 吞吐/队列 | ops/s、写入 bytes/s、在途操作、积压年龄 | 成功操作还是尝试数，队列从哪层计，限流和失败是否计入 |
| 容量/增长 | 可用字节、使用率、增长率、inode/对象数 | 逻辑/物理、预留/可用、压缩/副本/快照占用、扩容提前量 |
| 保护与恢复 | 最近备份点、复制滞后、恢复演练耗时 | 备份是否可读/可解密/校验；恢复覆盖了哪些数据和依赖 |

延迟分位数与 M12 相同：p99 是测量窗口内的经验阈值，不是下一时刻的 SLA 保证。若一个窗口只有 20 个请求，p99 基本落在最大值附近；必须同时报告样本数、错误和观测缺口。直方图桶过宽无法还原精细 percentile；不同节点 histogram 只有在 bucket 边界一致时才适合聚合。

## 2. 指标、日志与 trace 互补，而非互相替代

**指标（metrics）**是有界标签维度的时间序列，适合趋势、告警、容量和聚合：`storage_requests_total`、成功/失败率、延迟 histogram、队列深度、设备/池可用字节、OSD/PG 状态数量、复制滞后、最近备份成功时间、恢复演练年龄。Counter 通常单调增长（进程重启会重置）；Gauge 是某时刻值；Histogram 提供桶计数/总数/和。必须记录单位、counter/gauge 类型、采集间隔、reset、缺失值和聚合窗口。

**结构化日志（logs）**记录单个事件和上下文：时间、服务/组件、操作、错误码、对象/卷引用（按隐私策略脱敏）、节点/OSD、trace ID、错误原因和操作结果。JSONL/系统 journal 都是日志；应使用稳定字段、UTC 时间、明确 severity，限制敏感内容和保留期。日志能解释“哪个请求失败”，但高量事件会采样、丢盘、限速、被 rotation 删除或因时钟偏差难关联。

**Trace**将一笔请求跨进程/组件拆成有 parent-child 的 spans，例如：

```text
client Put
 ├─ API/auth/metadata
 ├─ CSI or engine queue
 ├─ filesystem / block layer
 └─ backend request → replica/OSD → completion
```

Trace ID/Span ID 用于关联日志，不是每个 span 都会长期保存：采样、collector 背压、网络分区、进程 crash 都会丢 trace。对存储路径，还要区分“收到请求”“写入 journal/WAL”“复制确认”“设备 flush”“向客户端 ack”的 span；trace 上的 span 完成仍不自动证明掉电持久性。

**同一事件三种视角：**指标发现某分钟 p99 上升；日志指出特定卷的 I/O timeout；trace 将慢请求定位到 CSI attach、OSD 后端或客户端重试。不能因某一种信号无事件就断言问题不存在。

## 3. 标签基数、成本与数据限制

Prometheus 时间序列近似为“指标名 × 每个 label 的值组合”。`operation={get,put,delete}`、`status={ok,error}` 是受控低基数维度；容量可使用固定 `pool`/`kind` 标签。禁止将对象 key、文件名、用户 ID、Pod UID、request ID、trace ID、任意错误文本作为 metrics label：每个新值都创建新序列，会放大内存、索引、网络、查询 CPU 和远端存储成本。高基数请求/trace 标识可按安全策略放在日志/trace 中，并限制采样、保留和访问权限；日志/trace 同样有成本和隐私风险。

聚合会丢失细节：节点 histogram 可以求和，但平均值不能简单平均多个节点平均值；聚合 counter 前要正确处理 reset；把多个租户压成总量会隐藏单租户热点。单个“99% 容量” gauge 也要结合增长速率和可扩容时间，百分比不同的池不能盲目平均。

遥测是有损采样：scrape 失败、exporter 不可达、队列溢出、时钟错误、采样、日志 rotation、网络切断都会造成空洞。仪表盘要把“无数据/过期”显示为 **unknown / telemetry gap**，不渲染成 0。对关键计数，比较应用计数器、日志事件和 exporter scrape 健康；它们可能都共享同一个故障源，不能简单多数表决。

## 4. 健康探针、容量与过载

- **Liveness：**进程是否能继续运行/是否死锁。失败后平台可能重启容器；把暂时后端故障当 liveness 会引发重启风暴。
- **Readiness：**实例是否应该接收新流量。依赖暂不可用、启动恢复未完成或过载可使 readiness false，而进程仍 live。
- **Startup：**给慢启动/恢复足够时间，在启动探针成功前避免其他探针过早重启。
- **存储健康：**还需检查该卷是否已挂载、读写 API 能否服务、集群副本/PG/仲裁状态及应用校验；HTTP `/health=200` 不是数据健康或 durability 证明。

容量不是单一“磁盘百分比”。区分设备原始空间、Ceph OSD/CRUSH 池可用空间、复制/EC 后逻辑容量、文件系统保留块、快照/克隆、临时卷、inode、对象数量和租户 quota。设阈值前估计增长速率、恢复/重建额外占用、扩容采购/调度延迟和系统保留余量。容量红线可能让写入被拒绝、触发 nearfull/backfillfull/full；不能等满盘后再设计恢复。保留旧快照/未清理临时对象也会吞噬空间。

过载时配合 M12 的背压：限制并发和待处理字节，定义拒绝/超时/重试，观察队列年龄和错误；不能通过无界重试让系统更慢。告警应指定接收者、分级和动作（先只读确认，再变更），避免“指标响了但没人知道做什么”。

## 5. RPO、RTO 与可恢复性

- **RPO（Recovery Point Objective）：**故障时可接受丢失的数据时间窗口。RPO=1 小时意味着恢复点最多落后约一小时；它不是“每天备份一次就自然满足”，还要计备份完成/校验、日志归档、复制滞后和故障发生位置。
- **RTO（Recovery Time Objective）：**从约定的中断起点，到业务恢复到约定服务等级的目标时间。包括检测、决策、准备资源、恢复数据、重放日志、校验、依赖恢复、切流与业务验证，不只是某个 `restore` 命令耗时。
- **备份**应有独立的故障域/权限/保留策略，记录一致性点、数据范围、加密密钥、manifest、校验和、软件格式版本和完成状态。仅有“上传成功”不证明文件可读、密钥存在或应用一致。
- **恢复演练**在隔离目标恢复具体备份，核对版本/对象数量/checksum/业务不变量，量时并记录人工步骤、失败和 cleanup。恢复时间只有对明确的数据量、拓扑、依赖和资源限制才有意义；定期演练还要验证恢复人员/凭据。
- **快照不等同备份：**同一阵列/集群/管理员账户中的 snapshot 可能随源故障或误删一起丢失；它可能只是 copy-on-write 引用，源池仍承担空间/故障风险。快照一致性还依赖应用 quiesce/文件系统 freeze/数据库 checkpoint；Crash-consistent 与 application-consistent 不同。

合成“最近成功备份时间早于 RPO”只能提示模型里的恢复点风险；合成“恢复测时超过 RTO”只能提示演练不满足目标。它们不执行真实备份/restore，也不能覆盖复制、WAL、灾难域和业务恢复全路径。

## 6. Lab 13：在 localhost 上采集并诊断

```sh
cd labs/lab-13-local-observability
python3 -m unittest -v test_observability_demo.py
python3 observability_demo.py --scenario healthy --requests 24 --seed 20261013
python3 observability_demo.py --scenario metrics-gap --requests 24 --seed 20261013
```

Demo 将一个临时 HTTP 服务**只绑定 `127.0.0.1` 的临时端口**，由客户端真实发起 loopback 请求。脚本生成 `localhost.jsonl` 结构化请求日志、`synthetic.prom` 有限 Prometheus 文本、父子 span 的 `traces.jsonl`、health 和诊断 JSON，保存在 `storage-lab13-*` 私有临时目录中。工具自动输出该目录；检查实际路径后只删除本次专属目录。

演示值的区别：localhost HTTP 时延是本机 Python 模型观测；容量、请求后端行为、备份时间和恢复用时是合成；它不打开存储设备，不写用户数据，不访问公网。Metrics parser 只支持演示器发出的有限格式，不是生产 scraper。输出 p95 是诊断练习，不是性能基准。

## 7. 故障诊断练习

对每个场景写“观察事实 → 可能解释 → 还需要什么证据 → 安全动作”，不要从一个告警跳到破坏性修复：

1. `latency`：比较 p50/p95/p99 与 histogram 桶；慢点集中在哪些请求？缺少 CPU、队列/等待时间、后端 latency 和重试 span 时，不能直接归因磁盘。
2. `capacity`：核对 used/total 与增长率；容量高不说明马上扩哪层。还需 pool/逻辑容量、快照、quota、扩容时间和安全余量。
3. `backup`：把最近备份 age 对 RPO、恢复演练 duration 对 RTO、演练 age 对新鲜度分别比较。此工具没有真的恢复数据。
4. `errors`：服务 live 但 not ready，先区分依赖失败、错误率、探针门槛与单个业务错误；重启不会修复持久化后端。
5. `metrics-gap`：日志有请求而 metrics 不完整；检查 exporter/scrape/标签过滤/队列。不得将指标空洞解释为零请求或健康。

每份报告额外写出：日志/metrics/trace 哪些字段可能丢失、为什么它们不独立、告警的误报/漏报代价，以及一个不触碰真实数据的下一步验证。

## 课后问题

1. API 成功率正常但复制滞后不断增长，用户何时可能看到不可恢复的数据损失？还缺哪些 durability 指标？
2. 为什么 `trace_id` 是合理的 log field，却通常不应成为 Prometheus label？
3. histogram bucket p95 与应用请求 p95 有什么区别？同一 histogram 不同 bucket 能否直接相加？
4. readiness=false、liveness=true 时平台应做什么？若两个探针共用同一个存储后端检查会有何级联风险？
5. 一周前备份“任务成功”，但没有 restore 验证和密钥清单，能否说满足 24h RPO/2h RTO？
6. 快照已 `readyToUse=true`，为什么仍需验证恢复 PVC 的业务数据和故障域？
