## 1. 主机看到的“覆盖”不是 NAND 原地覆盖

M01-L01 介绍的 LBA 是设备暴露的逻辑地址，主机并不知道一个 LBA 对应哪颗 NAND die、哪条 channel、哪一个物理页。典型 SSD 控制器在主机接口与 NAND 之间维护一层 **FTL（Flash Translation Layer，闪存转换层）**：接收逻辑读写，管理映射和空闲物理页，并处理介质管理。

NAND 的常见操作粒度可以这样理解：**读取/编程以 page 为基本单位之一，而擦除以更大的 erase block 为单位**。具体 page 尺寸、部分页编程限制、擦除块布局、并行单元与管理策略取决于 NAND 类型和控制器。一个已编程页不能像普通内存字节那样随意原地改写；要更新其中数据，常见 FTL 策略是把新内容写到另一可用物理页，再更新逻辑映射，旧物理页变成无效页。包含无效页的 erase block 之后才能整体擦除并复用。

```text
应用 / 文件系统：覆盖逻辑范围 (LBA 42)
          │  主机字节写入（可能先缓存、拆分或合并）
          ▼
Linux 块层 / NVMe 命令队列
          │  namespace LBA 42
          ▼
SSD 控制器与 FTL：查询/更新映射、分配物理页、搬迁和回收
          │
          ├─ NAND page P_old：旧数据失效，暂不一定可擦除
          ├─ NAND page P_new：写入新数据，映射改为 42 → P_new
          └─ GC：搬走仍有效页 → 擦除整个 block → 返回空闲块池
```

因此，“主机对 LBA 原地覆盖”是**逻辑语义**，不是对同一物理 NAND 页原地改写的承诺。控制器可能采用页级、块级或混合映射，也可能有多级缓存、压缩/去重、元数据日志、条带化及厂商专有算法；不能从接口或一个性能数字推断具体固件实现。

### FTL 不只是一张映射表

典型 FTL/控制器还要处理逻辑到物理地址映射及其恢复、空闲空间分配、GC、动态/静态磨损均衡、坏块管理、ECC/数据完整性、读扰动/刷新、TRIM/Deallocate 提示，以及掉电后的元数据一致性。不同控制器会把部分工作放在主机软件、设备 DRAM、NAND 元数据或专用保护电路里。设备支持的持久化/掉电保护能力必须按产品文档和接口语义验证；不能把 ioctl 返回、设备命令完成、flush/FUA 完成和 NAND 物理编程混为一谈。

`TRIM`/Deallocate 通常是在告诉设备某些逻辑范围的数据已不再需要，可帮助回收；它不保证设备立刻擦除对应 NAND，也不等同于安全擦除。NVMe namespace 格式、LBA、NVMe NLB 等主机接口单位仍按 L01 解释：它们不是 NAND page 或 erase-block 地址。

## 2. 一次覆盖的 FTL 生命周期

下面是教学用的简化**页映射**流程。假设逻辑页 L 映射到物理页 P0，主机提交一次更新：

1. **接收与校验**：控制器接收写命令，按 namespace 几何、对齐/边界和设备当前资源条件处理。主机请求可能先由内核/设备队列等待。
2. **选择新页**：FTL 从已擦除的空闲页中分配 P1。实现可能先写设备 DRAM/SLC 缓存，再稍后折叠到其他 NAND；这里不假设具体缓存策略。
3. **写新数据与映射**：将新数据编程到 P1，并按实现维护映射/元数据。满足什么条件才对主机确认，取决于缓存、flush/FUA、掉电保护及具体接口。
4. **旧页失效**：映射从 `L → P0` 转到 `L → P1`，P0 不再承载当前逻辑版本。P0 所在 erase block 仍可能包含其他有效页，所以不能只擦一个页来回收。
5. **垃圾回收**：当空闲页不足或策略认为合适时，GC 选择一个含无效页的 block，把其中仍有效的页复制到其他位置，校验/更新映射，再擦除整个旧 block，把它放回空闲池。

映射更新顺序、掉电中断时如何恢复、何时把数据从易失性缓存推进到持久介质，都不是这个示意图自动保证的事情。真实 FTL 会处理这些一致性问题，具体保证应以设备规格、管理工具说明和测试边界为准。

### GC 的数字例子

设一个 erase block 有 4 个页，其中 3 个仍有效、1 个无效。回收步骤需要把 3 个有效页复制到其他空闲位置，再擦除源 block，腾出后续写入空间。若这次为了使用新回收空间，只产生 1 页新的主机数据，则仅此局部过程就有：

```text
主机新写页         = 1 page
GC 搬迁页          = 3 page
NAND 编程页总数    = 1 + 3 = 4 page
局部写放大         = NAND 编程字节 / 主机写入字节 = 4 / 1 = 4×
```

若受害 block 有 3 个无效页，只需搬迁 1 个有效页，同样 1 页主机新写对应 2 次 page program，局部 WA 为 2×。若回收一个全无效块，不必搬迁有效页，这部分搬迁 WA 为 0；但仍会发生块擦除。这里的例子不包含映射元数据、设备缓存折叠、其他层的写入、ECC、压缩、坏块替换或条带冗余。

## 3. 写放大、空闲空间与访问局部性

### 指标定义要说明测量边界

对同一测量窗口，一个简化的 SSD **内部写放大**定义为：

```text
WA_device = NAND 实际编程字节数 / 主机提交给设备的逻辑写入字节数
```

在“每次请求整页、页大小相同、无压缩/元数据”模型中，可以用页数比代替字节比：

```text
WA_model = (主机新编程页 + GC 搬迁编程页) / 主机写页
```

该值通常至少为 1（本课模型不计入设备压缩减少写入的情形），但真实设备和厂商测量口径各异。系统/应用层还可能有 WAL、文件系统日志、CoW、RAID parity、复制和重试等写放大；不要把这些都称为 SSD FTL 的内部 WA。报告指标时标明分子/分母、时间范围、预处理/稳态和是否含元数据。

**WA 不是延迟或速度。**WA 高可能表示 NAND 要编程更多字节，但实际吞吐还取决于并行度、控制器、请求大小、队列、缓存、介质和 CPU 等；设备数据手册的 TBW/endurance 也不能由一次短测的 WA 直接换算。

### 空闲空间和过量配置

控制器需要已擦除物理页作为新写入和 GC 搬迁目标。主机可用 namespace 容量与设备内部物理容量之间通常留有空间；文件系统未分配空间、discard/TRIM 和设备保留区域也可能影响实际空闲余量。课程模型中将：

```text
OP ratio = (物理页总数 − 逻辑页数) / 逻辑页数
```

作为一个便于算例的过量配置比率定义。厂商有时采用不同分母、容量单位和可用容量口径，比较数字时应先统一定义。更多空闲页可能让 GC 有更多选择、减轻搬迁压力，但不能只看 OP 就保证某个 WA：工作负载寿命、覆盖模式、TRIM、保留空间、GC 算法和稳态都重要。

### 热点与冷数据

若频繁改写的“热”数据和长期不变的“冷”数据混在相同 erase block，回收某块时可能不得不搬迁仍有效的冷页。把热/冷数据分开放置能在一些场景减少有效页搬迁，但如果分类错误、对象生命周期变化或需要额外布局/元数据，也可能适得其反。主机顺序写不必然映射成 NAND 顺序写：FTL 可能重排、折叠缓存、GC 搬迁或跨多个介质单元写入。

- **热点覆盖**：少量 LBA 频繁更新，产生失效页；是否低 WA 取决于 GC 能否选到含足够无效页的 block。
- **均匀随机覆盖**：更新分布广，受害块常含较多仍有效页，搬迁量可能增加。
- **顺序写**：若顺序覆盖与设备内部回收边界/有效数据分布匹配，可能较容易回收；它不是任何设备上的吞吐保证。

### 磨损均衡

NAND erase block 有有限的擦写耐久，物理块被擦除次数可能不均。磨损均衡策略试图避免少数块过早耗尽：

- **动态磨损均衡**：新写入或新回收的块优先分配给相对低擦除计数的可用块。课程模型的 `least_worn` 只实现这种极简“从空闲池挑擦除次数最少者”的策略。
- **静态磨损均衡**：如果某些块长期保存冷数据且擦除次数低，控制器可能搬迁其中的数据，以便这些低磨损块也能参与后续写入，同时让已磨损较高的块承载冷数据。迁移会增加当下写入/擦除成本。

模型还使用贪心 GC：在已写满/关闭、含无效页的块中优先选择无效页最多者，擦除次数作为平手时的次级选择；刚写满的活动块也可以参与回收。真实固件需要在回收效率、尾延迟、擦除次数、温度、并行度和后台/前台资源间取舍，无法用单一策略完整表示。擦除次数 spread 只是 toy model 的观察值，不是寿命预测；静态磨损均衡、坏块替换与 ECC 都未实现。

## 4. 请求队列：队列深度不是“越大越快”

M01-L01 画出 Linux 块层到 NVMe 主机驱动的请求路径。Linux `blk-mq` 在软件队列、硬件 dispatch 队列和设备队列间分发请求；NVMe 通过 submission/completion queues 及完成通知处理命令。主机提交多个未完成请求可以提高设备并行处理机会，但实际能否并行取决于设备、驱动、CPU、请求位置、读写类型、队列数/深度与内部控制器资源。

**队列深度**是某个观察层面同时在途/排队的请求数，不是“SSD NAND die 数”，也不是单个应用 `write()` 数。一次大写可能被拆成多个块层请求或 NVMe 命令，多个小写也可能被合并；文件系统、块层、驱动、协议与设备内部均可能形成不同队列。设置高 `iodepth` 并不保证每层都达到同一深度。

当到达率低于服务能力时，提高并发有时能让设备保持忙碌、增加吞吐；在瓶颈饱和后继续增加负载主要会积累等待，p95/p99 延迟可能明显增加。Little 定律给出稳定系统中的关系：

```text
平均在系统中的请求数 L = 到达率 λ × 平均响应时间 W
```

例如 1000 IOPS × 0.010 秒 = 平均约 10 个在途请求；这是关系式，不是 SSD 性能预测。突发、服务时间长尾、后台 GC、限流、错误重试和非稳定过载会让简单平均模型不够用。比较性能还须固定请求尺寸/读写比、随机/顺序、对齐、并发与队列深度、预处理/稳态、缓存与同步语义、数据集、测量窗口和延迟分位数。

### 块大小实验不能只归纳为“调用少一定更快”

`dd bs=` 改变用户态读写缓冲/调用的批量，不保证一个 `write()` 对应一个 NVMe 命令或一次物理页编程；块层可能合并或拆分请求，队列深度、同步/缓存、设备状态、命令开销、介质并行、GC 和 CPU 都会影响结果。更大 I/O 可能减少每字节调用/协议开销、帮助顺序带宽，也可能增加单请求时延、排队、内存占用，或不适合小随机访问。应使用固定负载和方法测量，不能从单次结果推广规律。

## 5. 本地 NVMe 与远程块存储

“块设备”描述向主机呈现的接口/地址空间，不说明设备和主机是否在同一机箱、网络质量、故障隔离或服务承诺。

```text
本地 NVMe：应用 → VFS/块层 → NVMe 驱动/PCIe → 本机 SSD 控制器与介质
远程块：  应用 → 本机块层/传输 initiator → 网络 → 远端 target/服务层 → 远端块设备/存储后端
```

远程路径可使用 NVMe-oF（如 TCP/RDMA）、iSCSI、虚拟化平台或云供应商专有协议。来宾系统可能仍看到一个块设备，但真正的数据路径还包括虚拟化、网络、后端队列、复制/缓存/配额与服务端故障恢复。远程卷并不必然暴露真实 NVMe 或 FTL，也不能从 `/dev` 节点名称推断硬件。

| 方面 | 本地 NVMe（典型路径） | 远程块（NVMe-oF/云块等） |
|---|---|---|
| 主要路径 | 本机 PCIe、驱动、控制器、设备固件 | 主机栈 + 网络/传输 + 远端 target 或服务层 + 后端 |
| 延迟变量 | 主机调度、队列、介质/固件、缓存与 GC | 本地队列之外还包括网络 RTT/拥塞、target 队列、后端策略和多租户竞争 |
| 扩容与共享 | 通常与单机槽位/控制器/容量相关 | 可由平台独立配置/附加/迁移，但受网络、配额和供应商能力制约 |
| 故障域 | 设备、PCIe、主机、电源；设备故障常直接影响该主机 | 网络、initiator/target、后端、控制面、租户与供应商区域；边界由实现决定 |
| 可观测性 | 部分设备/队列/SMART/错误可本地查看，仍受固件限制 | 客户端能看到接口指标，但服务内部队列、复制与介质实现常不可见 |
| 持久化与一致性 | 取决于驱动/设备/flush/FUA/掉电保护 | 还要查传输 target 和服务产品对 flush、写确认、故障切换的定义 |

远程块存储可以用网络换取共享、弹性、迁移或集中运维，也引入额外延迟层与依赖；它不等价于对象存储。不同服务可能提供快照、复制、QoS 或 SLA，但必须针对具体产品/配置/区域查验，不能把产品承诺泛化到所有远程块设备。M00 的需求卡和工作负载描述方式同样适用：比较相同端到端测量点、数据、请求与故障假设。

课程必做内容只用本地模型讨论远程路径；本课不连接本地 target、VM 或云盘。任何之后的 loop/NVMe-oF 真机练习都必须是单独审核的可选实验，不能用真实设备写入替代本模型。

## 6. 本地合成实验：追踪 FTL 与排队

实验目录：[lab-02-ssd-ftl-model](../../labs/lab-02-ssd-ftl-model/README.md)。运行前先读实验说明。核心代码为 [`ssd_ftl_model.py`](../../labs/lab-02-ssd-ftl-model/ssd_ftl_model.py)，输入为 [`model.example.json`](../../labs/lab-02-ssd-ftl-model/model.example.json)，自测为 [`test_ssd_ftl_model.py`](../../labs/lab-02-ssd-ftl-model/test_ssd_ftl_model.py)。程序只读配置，并在内存中建模，不执行 I/O 测试。

```sh
cd labs/lab-02-ssd-ftl-model
PYTHONDONTWRITEBYTECODE=1 python3 -B -m unittest -v test_ssd_ftl_model.py
PYTHONDONTWRITEBYTECODE=1 python3 -B ssd_ftl_model.py model.example.json
```

第一条应运行 6 个标准库测试并得到 `OK`。第二条输出三类轨迹（4 页热点、全逻辑范围均匀访问、循环顺序覆盖）分别使用 FIFO / least-worn 分配的指标，以及一组队列摘要。模型几何为 20 个逻辑页、32 个物理页，4 页/block；初始化有 12 个空闲物理页，按本课分母定义 OP ratio 为 `(32−20)/20=60%`。运行期每次主机更新写一整页。

### 如何读结果

- `gc_copied_pages`：GC 因目标 block 仍含有效逻辑页而额外编程的页数。
- `write_amplification`：`(host 新编程页 + GC 搬迁页) / host 写页`。配置中初始映射不计入分子/分母。
- `erase_count_spread`：最高擦除数减最低擦除数，含仍未擦除的冷块；只能比较相同模型输入下的策略，不是硬件寿命指标。
- 队列 `p50/p95/p99_us` 包含 FCFS 等待、确定性的服务时间和配置给远程路径的 RTT。`network_rtt_us` 不占用模拟的 target service lane；这是为区分网络项和目标排队的简化假设。

基准配置的均匀 trace 输出中，FIFO 的 erase-count spread 为 2，least-worn 为 0；模型 WA 分别约 2.6375 与 2.625。远程队列 p99 约 5092 µs，低负载本地队列约 81 µs。**这些是配置参数和本课算法算出的玩具数值，不是产品对比、性能基线或预期 SSD 行为。**两类模型彼此独立：队列部分不根据 FTL GC 的模拟事件动态增加服务时间。

### 修改配置前后要写清假设

1. 将 `hot_pages` 改为 20，再运行，比较同一写次数/seed 的热点与均匀 trace；解释地址分布改变怎样影响旧页失效和 GC 有效页搬迁。
2. 只保留一种 `allocation_policies`，或把策略换成另一个，比较擦除计数 spread；说明模型只近似动态均衡，不含静态搬迁。
3. 将 `queue.interarrival_us` 从 100 改为 250，或增大 `remote.lanes`；分别解释降低到达负载和增加服务 lane 对排队的影响。
4. 将远程 `network_rtt_us` 改为 0；target 服务和排队仍存在。说明响应时延中的固定网络项、服务时间与排队等待如何分开。
5. 写下至少两项这个模型省略的真实成本/限制，并指出为什么结果不能推出设备 IOPS、TBW、SLA、故障恢复或持久性。

请不要把模型扩展成打开 `/dev`、对 loop 设备写入、执行 fio 或扫描真实硬件的工具。无需为验证 M01 安装 fio；若课程后续引入 fio 文件基准，必须另列固定版本、文件安全边界、缓存/同步设置和临时文件清理方法。

## 7. 设备单位、基准与安全边界

Linux 块层的 sector 使用 512 B 计数单位；这不等同于 NVMe namespace 的逻辑 LBA 大小，更不是 NAND page 大小。设备格式和接口单位必须分别确认。`dd bs=` 改变用户态读写缓冲与系统调用的批量，不保证一个 `write()` 对应一个 NVMe 命令或一次物理页编程；块层可能合并或拆分请求，队列深度、缓存、设备状态、写回、垃圾回收和 CPU 都会影响结果。

裸设备上的写入可能覆盖数据、分区或文件系统元数据。设备级性能测试必须在专用、可丢弃并明确隔离的目标上另行设计；课程主线只使用程序自建的普通临时文件与内存模型。基准报告应记录设备/固件、预处理、缓存与持久化口径、队列/并发、后台状态和重复结果，不能用两条不同参数的单次命令推导通用性能规律。

## 8. 练习题

1. 某 block 有 16 页，3 页无效、13 页有效。GC 搬迁所有有效页后擦除它；若下一批 host 写入 13 页，按本课简单页计数估算这段期间 WA。这个比值为什么不能代表一台 SSD 的稳态 WA？
2. namespace LBA 是 4 KiB，NAND page 是 16 KiB、erase block 是 256 pages（假设几何仅用于算术）。主机更新一个 LBA 时，为什么不能据此断言只改写一个 4 KiB NAND 区域？哪些 FTL 行为未知？
3. 某 trace 的 host 写入量相同，但均匀覆盖的 WA 高于热点覆盖。描述一个能产生这一现象的 victim 选择与有效页分布；再举例说明热点也可能导致高 GC 或磨损集中。
4. 设备 QD=1 与 QD=32 的平均吞吐增加、p99 延迟恶化。列出至少 4 个需要核对的负载/排队/测量因素，不能只说“高队列更快/更慢”。
5. 应用将普通文件写入远程块卷后收到了成功返回。列出需要核对的端到端路径、持久化和故障边界；“看到 `/dev/...` 节点”能证明哪些事，不能证明哪些事？
6. 两条块设备写入基准使用不同 `bs`，且目标是实际设备。指出数据损毁风险、单次结果的局限，并设计安全且能区分“系统调用批量”和“队列/服务能力”的实验方案（只需设计，不运行设备测试）。
